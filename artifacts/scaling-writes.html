Q1Burst or baseline

A queue sits in front of one database and accepts every write. The database persists at most 5,000 writes a second. The figure shows two traffic patterns. Both queues start empty. Which statement is correct?

Options for question 1

Solution

Answer: C

During the spike the queue gains 9,000 − 5,000 = 4,000 writes a second, so it holds 240,000 after 60 seconds. After the spike the database still takes 5,000 a second while 3,000 keep arriving, so the backlog shrinks by only 2,000 a second: 120 seconds. B measures the spike against the baseline instead of the limit. D forgets that new writes keep arriving while the queue drains.

Y is over the limit all day. No queue fixes that; it needs more write capacity.

Remember A queue borrows time. It is repaid only out of spare capacity: the limit minus the baseline.

Q2Before you shard

You show with quick math that one large machine can take the write load. The interviewer answers: “Fine. Now assume 50 times the traffic.” What does the article advise?

Options for question 2

Solution

Answer: A

The article says to make the case, and that most interviewers expect or appreciate it, staff-level candidates most of all. It also warns that many interviewers have an assessment built around horizontal scaling and will move the goalposts until you get there. So C goes too far, and B starts the argument the article tells you to avoid. D is wrong on the facts: a queue adds no capacity (Q1).

Remember Make the hardware case once, with numbers. Then follow the interviewer.

Q3Why append wins

Which statement gives the article’s reason that Cassandra takes more writes per second than a traditional relational database on the same hardware?

Options for question 3

Solution

Answer: B

Sequential appends are cheap; in-place updates need seeks. The article’s figures are 10,000+ writes a second against roughly 1,000 for the same work. The bill arrives on the read side: a read may have to look in several files and merge them. A gets the write side right and the trade wrong. C and D describe mechanisms the article does not claim.

Remember Append-only buys writes with reads. Name the trade, not only the database.

Q4Flat is not enough

A chat service stores 50,000 messages a second. By far the most common read is “load the latest messages of one conversation”. The article asks two questions of a partition key: how many shards does a request hit, and how often does it happen? Which key answers both best?

Options for question 4

Solution

Answer: D

A is the flattest for writes and the worst for the hot read: every page of a conversation gathers from every shard. B splits a conversation across the shards of its senders. C sends all of today’s writes to one shard. D is nearly as flat as A, because there are many conversations, and it answers the common read from one shard. A single huge conversation can still become a hot key (Q15).

Remember Pick the key that is flat for writes and local for the hot read. Ask: how many shards, how often?

Q5Slots

The figure shows how a Redis Cluster client writes a key. A fourth node now joins the cluster. What must change so that writes keep landing on the right node?

Options for question 5

Solution

Answer: B

There are two steps. Key to slot is a fixed hash. Slot to node is a table, and the table is what changes when the cluster grows. Only the keys in the reassigned slots move. A describes hash mod N, where adding a node moves almost every key; avoiding that is the reason for the extra step. (The Rate Limiter breakdown gives the number for Redis Cluster: 16,384 slots.)

Remember Key to slot never changes. Slot to node is a table you can edit.

Q6Does the batch help?

The Like Batcher in the figure writes one count update per post per one-minute window, and only for posts that were liked in that window. The site has 1,000 viral posts with 600 likes a minute each, and 10 million ordinary posts with about one like an hour each. What does batching do to database writes?

Options for question 6

Solution

Answer: A

A window helps only when it catches several events for the same key. A viral post has 600 likes in the window, so 600 writes become one. An ordinary post almost never has two likes in the same minute, so each like is still one write. This is the article’s staff-level point: a post with one like an hour gets nothing from a one-minute batch. C misreads the batcher, which writes only posts that changed.

Remember Batching pays per key, per window. One event in the window means no saving.

Q7Agreeing on hot

A system splits a like counter into sub-keys only when a writer finds that the key is hot. Readers and writers must agree on which keys are split. Which design does the article say most production systems use?

Options for question 7

Solution

Answer: C

C is simple and safe: a reader can never miss a split, because it always looks. The cost is the same read amplification as splitting every key. A is the article’s second, more burdensome option; it avoids reads of sub-keys that do not exist. B is the other deep-dive answer (split all keys), not this one. D fails: a reader and a writer keep different statistics, so a reader can miss sub-keys and under-count.

Remember Writers split when hot. Readers always check every sub-key.

Q8Strava

The Strava breakdown must support 10 million concurrent activities. Its first design sends every GPS point to the server: one every 2 seconds on a ride, every 5 on a run. Which change does the breakdown make, and what does it depend on?

Options for question 8

Solution

Answer: D

The server never needed each point during the run; distance and route are worked out on the phone. Sending once at the end cuts requests to the backend about 100 times, and offline tracking comes with it. C leaves out the local save, which limits a crash to about 10 seconds of data.

B is the pattern article’s rule, and the article names Strava as its example. It is the right tool when the pings must still reach the server. That happens if live sharing is added: the phone then sends every 2 to 5 seconds again. The breakdown’s first move is different: do not send the writes at all.

Remember The cheapest write is the one the client never sends. Batch at the source first; shed what must still arrive.

Q9FB Post Search

In the FB Post Search breakdown about 100,000 likes arrive a second, and results can be sorted by like count. Which approach goes furthest in cutting writes to the like-sorted index?

Options for question 9

Solution

Answer: C

With power-of-2 milestones a post with a million likes has caused about 20 index writes. The index is then only roughly ordered, so the query fetches more candidates than it needs and re-orders them with exact counts. D saves the same writes and returns a wrong order. B helps, and the breakdown’s final design keeps a like batcher, but alone it is weak for the reason in Q6: most posts get few likes per window. Post creation is the other write problem. A 100-word post is 100 or more index writes, so the breakdown buffers posts in Kafka and shards the index by keyword.

Remember Write the index at milestones. Fix the order at read time.

Q10Rate Limiter

In the Rate Limiter breakdown every request triggers a check that reads and updates a counter (a token bucket) in Redis. At about 1 million requests a second, one Redis node cannot keep up. Which change spreads the load and keeps the limits correct?

Options for question 10

Solution

Answer: A

A check is a read-modify-write, so it is write load, and replicas do not help (B). The bucket is per client, so the client is the unit that must stay together: A. C is flat and useless, because one client’s requests would update a different counter on a different shard each time. D makes a busy endpoint a hot shard. One Redis node manages perhaps 50,000 to 100,000 checks a second, so the breakdown spreads the buckets over about ten shards. One very busy client can still be a hot key (Passage V).

Remember A limiter check is a write. Shard by whatever the limit is counted for.

Q11Job Scheduler

The Job Scheduler breakdown handles about 10,000 jobs a second. Its Executions table uses the hour of the scheduled time (time_bucket) as the partition key, so that the poller finds everything due soon in one or two partitions. What problem does this key create, and how does the breakdown fix it?

Options for question 11

Solution

Answer: B

The time bucket was chosen for the read. Its cost is on the write side: DynamoDB allows about 1,000 write units per partition, and an hour of executions needs far more. The suffix is the article’s sub-key split applied to a partition key. Writes spread over the shards, and the reader pays by querying all of them. C gives flat writes but turns the poller’s query into a scatter across every partition, all day; A describes that state. D cannot help, because the load is steady and not a burst.

Remember Key for the read, then salt the key for the write. The reader queries every salt.

Q12Metrics Monitoring

In the Metrics Monitoring breakdown 500,000 servers each emit 100 data points every 10 seconds: 5 million points a second. Where is batching the safest and most effective first step?

Options for question 12

Solution

Answer: D

D turns 5 million requests a second into 50,000 without adding delay, because the points are produced in 10-second groups anyway. If a batch is lost, one host loses 10 seconds. A confirms data that exists only in memory, so a crash loses points that the sender believes are safe. B is the article’s “big hammer” for extreme cases. C ignores that a few seconds of batching fits easily inside a one-minute budget.

The breakdown says its ingestion path uses three of the article’s four strategies: batching at the edge (the agents), a queue for bursts (Kafka), and a write-optimised store (a time-series database). Its stated aim is to stop 5 million metrics a second from becoming 5 million requests a second.

Remember Batch as far upstream as you can, where a lost batch is small and can be sent again.

Q13What a queue buys

A write queue (Kafka or SQS) is placed between the app servers and the database. Which statements are correct?

Options for question 13

Solution

Answer: A, B, D

A and B are the price of going asynchronous. D is the benefit. C is the common mistake: capacity is still the database’s. If arrivals stay above it, the queue grows without bound and users wait on writes they were told had been accepted.

Remember Queue for bursts that end. Never to patch a database that cannot take the steady load.

Q14Vertical partitioning

The posts table is split into post_content, post_metrics and post_analytics. Which statements are correct?

Options for question 14

Solution

Answer: A, C, D

Content is written once and read often. Metrics are updated constantly. Analytics are append-only. In one table each kind of work gets in the way of the others. B is false: one post’s metrics are still one row on one server. That is a hot key, and it needs sub-keys (Q15).

Remember Vertical splits by access pattern. Horizontal splits by key. A hot key needs neither; it needs sub-keys.

Q15Split every key

Every like counter is split into k = 4 sub-keys, as in the figure. Which statements are correct?

Options for question 15

Solution

Answer: B, C, D

B is the gain. C and D are the costs the article lists: read volume and data size both multiply by k, for every post. A is false. A count can be kept in parts and added up; a profile must stay whole. If a small k brings the hottest key within one shard’s capacity, the problem is solved.

Remember Sub-keys work only for values you can add up. Reads pay k times.

Q16Resharding

A cluster grows from 8 shards to 16 with no downtime, as in the figure. Which statements match the article?

Options for question 16

Solution

Answer: A, B, D

C is the naive approach: take the system offline, rehash, move. For a large dataset that is hours of downtime. Production systems migrate gradually. The copy moves old rows, the dual write covers anything that changes meanwhile, and reads lean on the new shard.

Remember Reshard by dual-write, copy, then read from the new.

Q17Tuning one database

Which changes raise the write throughput of a single general-purpose database, at the cost stated?

Options for question 17

Solution

Answer: A, B, C

A, B and C are the article’s three tuning levers. Each one removes work from the write path and moves a cost somewhere else. D is false: replicas take reads off the primary, but every write still happens on the primary and is then shipped to each replica.

Remember Strip the write path: fewer indexes, grouped log flushes, no triggers. Replicas scale reads only.

Q18YouTube Top K

In the YouTube Top K breakdown, 70 billion views a day arrive on a Kafka topic partitioned by video ID. Which statements match the breakdown?

Solution

Answer: A, C, D

A and C are the breakdown’s arithmetic (it uses 100,000 seconds a day to keep it easy). D holds because a video cannot be split between shards. B has it backwards twice: batching cuts the number of writes, by 2 to 100 times, and they now arrive in a lump each hour. Q19Hierarchical aggregation

The figure shows the article’s design for live comments. Which statements are correct?

Write processors aggregate on the way in, and broadcast nodes fan out on the way out. No single component handles the full stream. Q21Autoscaling
Assertion
Autoscaling the database is a weak answer to a write burst that lasts a few minutes.
Reason
Scaling a database takes time, and it often brings downtime or lower throughput while it happens.
Options for question 21

Solution

Answer: A

Both are true, and the Reason is why. The article also gives the arithmetic of the alternative: to survive a 4× peak on capacity alone, you must run at 25% the rest of the time. So the choices are to buffer the burst or to shed part of it.

Remember A database scales too slowly for a burst. Buffer it or shed it.

Q22Even keys, uneven load
Assertion
Sharding by hash(userId) gives every shard nearly the same write load in any system.
Reason
A good hash spreads keys evenly across shards.
Options for question 22

Solution

Answer: D

The Reason is true. The Assertion is false, because an even spread of keys is not an even spread of writes. One user, post or ad can produce more writes than a whole shard can take: the viral tweet at 100,000 likes a second. That is the hot-key deep dive.

Remember A hash spreads keys, not load. One key can still be too hot.

Q23Capacity
Assertion
A queue lets a system survive a short burst that its database could not absorb directly.
Reason
A queue raises the rate at which the database can persist writes.
Options for question 23

Solution

Answer: C

The Assertion is true. The Reason is false. The database persists at the same rate as before; the queue only holds what it has not reached yet. Believing the Reason is how a queue comes to hide a database that is too small.

Remember A queue moves writes in time. It adds no capacity.

Q24What can be split
Assertion
A like counter can be split into sub-keys, and a user profile cannot.
Reason
Like counters are written far more often than user profiles.
Options for question 24

Solution

Answer: B

Both are true, and the article says both. But the Reason is not why. A counter can be split because its parts can be added back together. A profile must stay atomic. The Reason only explains why this limit rarely hurts: data that must stay atomic is seldom under that much write pressure.

Remember Split what you can sum. Keep atomic data whole.

Q25Right tool, wrong query
Assertion
The Top K breakdown rates InfluxDB and Prometheus a bad fit, although the article lists time-series databases as built for high-volume writes.
Reason
Those engines suit heavy writes and narrow queries on one series, but a top-K query must look across billions of video IDs at once.
Options for question 25

Solution

Answer: A

Both are true, and the Reason explains it. With a video ID as the series label there are billions of series, and “top” over all of them is a scan. A write-optimised store solves the write problem only; the read still decides. The breakdown rates TimescaleDB and real-time OLAP stores as good, because they keep pre-aggregated rollups.

Remember Choose the store by the query as well as the write rate. High cardinality breaks time-series engines.

Q26Job Scheduler
Assertion
The Job Scheduler breakdown calls a Kafka queue between the API and the job-creation service likely over-complication.
Reason
A queue cannot absorb a burst of job creations.
Options for question 26

Solution

Answer: C

The Assertion is true and the Reason is false. A queue can absorb the burst; the breakdown’s point is that this one is not needed. The database should take the write rate directly, and a service that scales horizontally has to sit in front of it in any case. The queue earns its place only if job creation carries expensive logic worth isolating.

Q27FB Post Search

FB Post Search should be designed as a read-heavy system, because it is a search product.
Reason
It serves about 10,000 searches a second.

Answer: D

The Reason is true and the Assertion is false. Against 10,000 searches a second the breakdown counts 10,000 new posts and 100,000 likes. Q28Strava
Assertion
The Strava breakdown shards its database by the time an activity was completed, although a time-based key sends all new writes to the newest shard.
Reason
Once tracking moves to the phone, the server takes about one upload per finished activity, so the write rate is low. The sharding is for data volume and for queries that mostly want recent activities.

Answer: A

Both are true, and the Reason explains why the usual objection does not apply. About 100 million activities a day is roughly 1,000 writes a second, which one node can take. Q29First tool

Match each situation with the first technique to reach for.

Column I

  1. PSustained writes are five times what one node can take.
  2. QWrites exceed capacity for two minutes at the top of each hour, and a short delay is acceptable.
  3. RDevices send fresher data every few seconds, and under overload the stored data goes stale.
  4. SOne counter takes 100,000 increments a second, which is more than a whole shard can take.

Column II

  1. 1Load shedding
  2. 2Sharding
  3. 3Sub-key split
  4. 4Write queue
  5. 5Read replicas
Options for question 29

Solution

Answer: C

P is a capacity problem, so add capacity by sharding. Q is a short burst with tolerance for delay: queue it. R is data that replaces itself: shed it. S is a single hot key: neither more shards nor a queue helps, because all the writes go to one place. Read replicas help none of them.

Remember Sustained: shard. Short burst: queue. Self-replacing: shed. One hot key: split.

Passage I: YouTube Top K

A stream of view events arrives on a Kafka topic that is partitioned by video ID: about 70 billion views a day, or roughly 700,000 a second. Q32One key, two layers

Why is the database sharded by the same key that the topic is partitioned on?

Options for question 32

Solution

Answer: B

The breakdown calls the partitioning a “seam” that runs through the whole pipeline: one partition, one consumer, one shard. It also makes the merge exact (Q18). A is the opposite of what happens: a single video always lands on one shard, which is why a very popular video is a hot-key risk, not a flat load.

Remember Carry one partition key through the pipeline: topic, consumer, shard.

Q33Seventy to ten

With hourly batching the breakdown expects the shard count to fall from about 70 to between 5 and 10. What explains the fall, and what new behaviour appears?

Options for question 33

Solution

Answer: D

Views concentrate on a small number of popular videos, so a per-video sum removes most of the writes (2 to 100 times fewer). The price is the shape: a lump at the end of each hour instead of a steady stream. C is a later variant in the breakdown, where all state stays in Flink; it is not this design.

Remember Batching trades a steady stream for fewer, lumpier writes.

Q34Shed the views?

Consumer lag is growing. A teammate suggests dropping some view events until it recovers, “as the article does with location pings”. What is the best judgment?

Options for question 34

Solution

Answer: A

Load shedding is safe when a fresher write will replace the lost one. A view is a fact that happens once. C is tempting, but a video outside the top K can climb into it, and its count must be right when it does. If the interviewer relaxes “precise”, the breakdown’s answer is an approximate count (a count-min sketch), which is a different trade made on purpose.

Remember Shed only what will be sent again. Counts that must be exact are never shed.

Passage II: Ad Click Aggregator

Questions 35 to 37 refer to this passage.

Clicks arrive at about 10,000 a second at peak, across some 10 million active ads. A click processor writes each click to a stream partitioned by ad ID. A Flink job sums the clicks of each ad per minute and writes the sums to an OLAP database that advertisers query. Q35The Nike ad

What does the breakdown do about the overloaded partition?

Options for question 35

Solution

Answer: C

All clicks with the same key go to the same partition, so more partitions do nothing for one ad (A). The suffix turns one key into N + 1 keys. The breakdown applies it only to popular ads, judged by ad spend or earlier click volume, which is the article’s “split hot keys dynamically”. B is “split all keys”: it works, and it multiplies keys and reads for 10 million ads that did not need it.

Q36Putting it back

With the suffix in place, the hot ad’s clicks for one minute are summed in N + 1 separate pieces. Where does the breakdown put them back together?

Options for question 36

Solution

Answer: B

Each click went to exactly one piece, so the pieces add up to the truth. The only question is who does the adding. The pattern article has readers sum every sub-key. The breakdown does it once, on the write side, and calls that cleaner for query speed; A is its stated alternative. C loses clicks, because an overwrite keeps one piece. Remember Sub-keys must be summed somewhere. Summing at write time keeps the read cheap.

Q37Rows per minute

Writing one OLAP row per click would mean about 600,000 rows a minute at peak. How many rows does the one-minute sum write, and what does the saving depend on?

Options for question 37

Solution

Answer: A

The sum is keyed by ad and minute, so the rows written equal the distinct ads clicked in that minute. If 600,000 clicks fall on 50,000 ads, that is a 12-fold cut. If every click were on a different ad, there would be no cut. It is Q6 with ads in place of posts.

Remember An aggregate writes one row per key per window. Count distinct keys, not events.

Solution

Answer: D

Q39Behind the campaign

With the single queue in the figure, the login code is queued one second after the campaign. Roughly when is it sent, and what is the fix?

Options for question 39

Solution

Answer: B

A million messages at 5,000 a second take 200 seconds, and the code is behind all of them. A fails twice. Q40What may be lost

The SMS provider starts throttling. By the article’s reasoning on load shedding, which policy is right for this system?

Options for question 40

Solution

Answer: C

Shedding is a business decision about which writes matter least, and it applies only where the loss is acceptable. Here the stated requirement forbids dropping anything accepted, so the release valve is delay, and only for the bulk lane. The breakdown says the same of a provider brownout: keep high-priority messages moving and let everything else wait it out, with a circuit breaker and a cap on calls in flight so that a slow provider cannot pin every worker. A copies the location-ping argument into a place where it does not fit: a missing code is a user who cannot log in.

Remember Shedding needs the business’s consent. Without it, the valve is delay, on the bulk lane only.

Passage IV: Flash Sale

A shop releases 10,000 pairs of a limited shoe at noon. Tens of millions of people try to buy within seconds. A buyer first reserves a pair for a limited time, then pays through a third party, which takes seconds. The design must never oversell. In the first design the stock is a single inventoryCount on the product row in Postgres. Each reservation runs UPDATE … SET inventoryCount = inventoryCount − 1 WHERE inventoryCount > 0 in the same transaction that inserts the reservation. The figure shows the final design.

Q41The hot row

The conditional UPDATE in the passage is correct: it can never oversell. Why is it still the bottleneck, and which fix does the breakdown choose?

Options for question 41

Solution

Answer: D

The breakdown’s picture is a shop with one register: hiring more cashiers (B) does not help. Redis is a much faster register, but it is still one hot key, and it splits the source of truth between two systems (A). With one row per pair there are 10,000 rows that lock independently, and Postgres can skip the locked ones (FOR UPDATE SKIP LOCKED). This is the article’s hot-key split taken to its limit: stock is a sum, so it can be divided, here down to single units.

Remember Correct is not the same as fast. Split the hot row into rows that lock independently.

Q42The ceiling

With the hot row gone, load tests show that the database commits about 10,000 reservation transactions a second. Millions of requests arrive in the first seconds. What does the breakdown do?

Options for question 42

Solution

Answer: A

The breakdown is blunt: no cleverer query exists, because this is a capacity limit. So it controls how fast users reach the write path. Its Scaling Writes note names the two steps: partition the writes across many rows, then absorb the burst with queueing and load shedding, which is the waiting room’s job. D fails because every instance ends at the same database. C promises a pair before the claim has committed. B buys huge capacity for a burst that lasts seconds and can sell only 10,000 pairs.

Q43Reserve, then pay

In write-scaling terms, why does the design reserve a pair first and take payment afterwards?

Solution

Answer: B

The breakdown says it directly: payment takes seconds, and inventory cannot sit in an open transaction for that long. The reservation takes the pair off the table at once and settles the money later. Passage V: Rate Limiter

A rate limiter in the API gateway keeps one token bucket per client in Redis. It must check 1 million requests a second and add less than 10 ms to each. One Redis node handles about 100,000 to 200,000 simple operations a second. A check reads the bucket, refills it, takes a token and writes the result. The breakdown runs all of that as one Lua script, so that two gateways cannot both spend the last token. The buckets are spread across Redis shards by a hash of the client identifier, as in the figure.

Q44Checks, not operations

Roughly how many checks can one Redis node take, and what follows for the design?

Options for question 44

Solution

Answer: C

A check is several operations, so the breakdown halves the node’s figure and lands on about ten shards for 1 million requests a second. D mixes up two things. Every gateway must see the same bucket for one client, and it does, because that client always hashes to the same shard. Different clients can live on different shards. In production the breakdown would let Redis Cluster do the routing, with its 16,384 hash slots.

Remember Count writes per request, not requests. Then divide by what one node can take.

Q45A hot client

One API key sends 50,000 requests a second and overloads its shard. What does the breakdown do?

Options for question 45

Solution

Answer: B

The article’s sub-key split suits a counter that is written often and read rarely. A limiter reads the bucket on every request, so A multiplies the reads on the hottest path and breaks the atomic check. C fails because a check writes. D is what the breakdown rejects for interactive traffic (next question). So the hot key is handled outside the data store: stop bad traffic early, and reduce good traffic at its source.

Remember Not every hot key can be split. Sometimes the fix is less traffic, not more shards.

Q46Queue or reject

A client goes over its limit. The article’s two ways to handle excess writes are to buffer them or to drop them. Which does the breakdown choose for an interactive API?

Options for question 46

Solution

Answer: A

The breakdown fails fast. Queued requests hold memory, users assume failure and retry, which adds load, and response times become unpredictable. Queueing fits only work that can wait, such as batch jobs. A beats B because the headers let a well-behaved client back off for the right time and stop hammering the API.

Passage VI: Metrics Monitoring

Questions 47 to 49 refer to this passage.

A monitoring platform watches 500,000 servers. Each emits 100 data points every 10 seconds: 5 million points a second, about 1 GB a second. An agent on each server sends its points in batches to an ingestion service, which publishes them to Kafka. Consumers write them to a time-series database, which dashboards and alert rules query. Dashboards may lag a little. An alert must fire within one minute of the data that causes it.

Q47Catching up

The consumers are down for 5 minutes, and Kafka holds the points. In normal running the pipeline uses 75% of its capacity. After the consumers restart, how long until the system is back to real time?

Options for question 47

Solution

Answer: C

The backlog is 5 minutes of traffic at 75% of capacity. Only the spare 25% can work on it, because live traffic keeps arriving. 5 × 75 ÷ 25 = 15 minutes. At 50% load the answer would be 5 minutes; the breakdown gives both figures. It is Q1 again: a queue is repaid out of spare capacity only.

Remember Catch-up time = outage × load ÷ spare capacity. At 75% load, three times the outage.

Q48Behind for good

The same 5-minute outage happens when the pipeline is at 95% of capacity, so catching up would take about an hour and a half. What does the breakdown prefer?

Options for question 48

Solution

Answer: D

The breakdown calls the queue a possible curse here: it faithfully keeps data that nobody can use in time. An alert that fires 90 minutes late has failed. So the choice is to run with real headroom or to cut losses, and for most monitoring systems losing some data is better than running behind. B drops the points that matter most. C only moves the backlog onto 500,000 servers.

Remember A backlog you cannot clear in time is a liability. Decide beforehand what you will drop.

Q49Too many series

A team adds a user_id label to a request metric. The number of points a second barely changes, but the number of distinct series grows by millions. Why does this hurt the write path, and what does the breakdown do?

Options for question 49

Solution

Answer: B

Write cost depends on how many series there are, as well as on how many points arrive. The breakdown enforces a policy before Kafka: allowed label keys, a series cap for each metric, a Redis set that tracks which series exist, and a counter for what is dropped. That counter is itself a metric to alert on. It is load shedding by another name: refuse the writes that would damage everyone’s writes. D only delays the same cost.

Remember Write cost is per series as well as per point. Cap series at the door, and count what you drop.
