Locks held vs. locks written

2026-11-18

Read this top to bottom. Each answer raises the next question.

Part 1: Holding a lock

Two users click seat A15 at the same moment. Only one of them can get it. Two tools come up: a pessimistic lock and a distributed lock.

Q1. What is the difference between them?

A connection holds a pessimistic lock. A distributed lock is a value written to shared storage.

A held lock ends when its holder ends: at commit, at rollback, or when the connection drops. A written lock ends at its expiry time or when code deletes it.

In restaurant terms, a held lock is a guest in the chair. Other guests wait at the door until that guest leaves. A written lock is a reservation card on the table. The guest can leave, and the card keeps the table.

The guest in the chair is the held lock. The card is the written lock.

Start with the guest in the chair. What happens to the next guest?

Q2. What happens when a second transaction wants the locked row?

It waits. Transaction A holds A15 with SELECT … FOR UPDATE. Transaction B runs the same query and blocks in the lock-wait queue. When A commits or rolls back, B gets the lock and reads the row as A left it.

Waiting with no limit sounds bad.

Q3. Does B ever stop waiting?

Only in these cases:

  • B asked not to wait. SELECT … FOR UPDATE NOWAIT fails at once if the row is locked. B must add NOWAIT itself. The default is to wait.
  • A lock timeout ends the wait. PostgreSQL has none by default (lock_timeout = 0), so B can wait forever. MySQL stops after innodb_lock_wait_timeout, 50 seconds by default.
  • A deadlock occurs. The database aborts one transaction and sends it an error.

After an error, your code decides whether to retry or to show “unavailable.”

The top row is the normal path. The red boxes are the only ways B gets an error instead.

Do readers get stuck in that queue too?

Q4. Does a plain read wait?

No. A plain SELECT without FOR UPDATE reads the last committed version of the row. To make this possible, the database keeps old versions of rows for readers that still need them. Only writes and locking reads wait.

So readers are fine. Then why not keep the row lock for the whole 10-minute checkout?

Q5. What breaks if a transaction stays open for 10 minutes?

Four things:

  • Other writers queue. With PostgreSQL defaults, every other request for A15 waits up to ten minutes, and each waiter is also an open transaction.
  • The connection pool empties. Each open transaction pins one connection. With a pool of 50, 50 users in checkout use every connection.
  • The next click can reach another server. A transaction lives on one connection in one app server. The user's “Pay now” request can reach a different server, which cannot continue the transaction.
  • Old row versions pile up. This follows from Q4.

If the app server hangs instead of crashing, its connection still looks alive. The lock stays until something closes the connection.

Why would old row versions pile up?

Q6. How does one old transaction make tables grow for everyone?

The database keeps an old row version while any open transaction might still need to read it. PostgreSQL's vacuum can remove a dead version only after every transaction that could see it has ended. InnoDB, MySQL's default storage engine, keeps old versions in its undo log for the same reason.

So one transaction that stays open for ten minutes holds back cleanup for ten minutes. Every update in that time leaves a dead version behind. Tables and the undo log grow, and queries scan more data.

The pile grows for as long as the checkout transaction stays open. InnoDB's undo log grows the same way.

Part 2: The lock in the same database as the data

So the hold must outlive the transaction. Where can it live?

A distributed lock can live in the same database as the data, or in a separate lock service such as Redis, ZooKeeper or etcd. Part 2 covers the first case. Parts 3 and 4 cover the second.

Q7. How do I hold a seat for 10 minutes without an open transaction?

Write the hold as data, in the same database as the seat, and commit at once:

-- 12:00: user 123 claims A15
UPDATE seats
SET    reserved_by    = 'user123',
       reserved_until = now() + interval '10 minutes'
WHERE  seat_id = 'A15'
  AND  status  = 'available'
  AND  (reserved_until IS NULL OR reserved_until < now());
-- 1 row updated:  user 123 owns the hold
-- 0 rows updated: another user owns it, so show "unavailable"

The transaction lasts milliseconds. After the commit, only a row remains. It says user123 owns A15 until 12:10.

No transaction is open now. What keeps the hold alive, and what does the next user see?

Q8. What happens after the commit?

No process holds the hold. It is a committed row that every app server can read, so an app server crash does not end it. Only its expiry time or a delete ends it.

User 456 runs the same UPDATE, matches zero rows and sees “unavailable” in milliseconds. After 12:10 the same statement succeeds, and no cleanup job is necessary.

With the held lock, user 456 waits up to ten minutes. With the written lock, user 456 gets an answer in milliseconds.

Two users can still click in the same millisecond.

Q9. Who wins if two users claim A15 at the same moment?

The claiming UPDATE takes a short row lock, and that lock puts the two claims in order. The second UPDATE waits a few milliseconds. Then it checks the WHERE clause again and matches zero rows.

Read it top to bottom. The row lock lasts only from the claim to the commit.

So every written lock is born from a short held lock. Hold a lock for milliseconds to make a decision atomic. Write a lock as data to keep ownership for minutes.

The claim is safe at 12:00. Is the hold still safe at 12:11?

Q10. Does a written lock always know its owner?

No. A held lock dies with its owner, so its owner is always current. A written lock can outlive its owner's turn. User 123 can click Pay at 12:11, after the hold expired and user 456 claimed the seat. User 123's server still thinks it owns A15.

Then user 123's server should check the hold just before it writes.

Q11. Why doesn't checking the hold first solve it?

Because the check and the write are two separate steps. The server checks at one moment and writes at a later moment. If it pauses between the two, the hold can expire in the gap, and the server cannot know.

Checking again does not help, because the pause can fall between the new check and the write. This pattern is called check-then-act, or TOCTOU (time of check to time of use). Only a check inside the write itself closes the gap.

This gap exists for every distributed lock, wherever it lives. Q12 closes it when the lock is in the same database. Fencing tokens (Q20 to Q24) close it when the lock is in a separate service.

The top shows the race. The bottom is the fix in Q12, where the check and the write are one statement.

So the write itself must check ownership.

Q12. How does the final write check ownership?

Put the ownership test in the WHERE clause of the booking:

-- user 123 completes checkout
UPDATE seats
SET    status = 'booked', booked_by = 'user123'
WHERE  seat_id = 'A15'
  AND  reserved_by    = 'user123'
  AND  reserved_until > now();
-- 0 rows updated: the hold is lost, so do not confirm the booking

This works because the hold and the seat live in the same database. One statement checks and writes as one atomic step. Use the database clock (now()), so clock differences between app servers cannot change the result.

This is the same-database form of a fencing check. A fencing token (Q20) carries the lock's state to the database when the lock lives in a separate service. Here the lock is already in the database, so the write checks the hold columns directly and needs no token.

The check is also stricter than a token. It rejects user 123 as soon as the hold expires, even if nobody else claimed the seat.

Every code path that books a seat must use this check. The hold is advisory, so a write that skips the check ignores it.

Payment happens in a different system, so it cannot join that atomic step.

Q13. When do I charge the card?

Only after you confirm or extend the hold. Make the charge refundable, because the payment provider and the database cannot commit together.

Part 3: The lock in a separate service (Redis as the example)

Many teams keep the hold in Redis instead. It is fast, and it deletes expired keys by itself.

This part uses Redis as the example, but the problems and fixes apply to any lock service outside the database, including ZooKeeper and etcd. Only the commands in Q14 and Q17 and the failover risk in Q16 are specific to Redis. Part 4 covers what ZooKeeper and etcd add.

Q14. How does a Redis lock work?

Server A works for user 123, and server B works for user 456. Server A takes the lock with one atomic command:

SET lock:A15 server-a NX PX 10000

NX sets the key only if it is absent, so two servers cannot acquire the lock at the same time. PX sets the TTL (time to live) to 10 seconds. After that, Redis deletes the key.

This is the same setup as Part 2, with the lock in a different place. Does the stale owner from Q10 come back?

Q15. Does the stale owner come back with Redis?

Yes. Here it is called the paused server. Server A gets the lock and then freezes, for example in a long GC pause. Redis deletes the key at 10 seconds and gives the lock to server B. Server A wakes up and still writes.

Server A freezes at 3 seconds. Redis deletes the key at 10 seconds and gives the lock to server B at 11 seconds. Server A wakes up at 17 seconds and still writes.

Did Redis do something wrong?

Q16. Is the expiry a Redis bug?

No. The expiry proves that Redis stopped listing server A as the owner. It does not prove that server A stopped working.

Redis has a second risk on failover. Redis copies data to replicas asynchronously. If the primary fails before it copies a new lock key, the promoted replica does not have the key, and another server can get the same lock.

But NX is a conditional write. Doesn't it check that server A still owns the lock?

Q17. Doesn't NX, or an owner check, stop server A?

No. NX works only at acquire time. It stops Redis from creating a second key while one exists. It never sees server A's later database write.

Storing the owner in the key and checking it before the write is the check-then-act race from Q11 again. Server A checks and sees its own name. Then it pauses, the TTL ends, server B gets the lock, and server A writes anyway.

Redis knows that server B owns the lock now. Why doesn't Redis block server A?

Q18. Why can't Redis stop the stale write?

Redis sees only the commands that acquire, renew and release the key. Server A sends its UPDATE straight to the database. Redis is not on that path.

The red path never passes through Redis. That is the gap a fencing token closes.

If Redis is not on the path, could server A write without any lock at all?

Q19. Can a server write without holding the lock?

Yes. Nothing stops it. Every distributed lock is cooperative, in Redis, ZooKeeper and etcd alike. A lock coordinates servers that follow the rules. It is not an access gate in front of the database.

So the protected resource must enforce safety itself. It needs a way to tell a current writer from a stale one.

A hotel has the same problem with old key cards.

Q20. How does a hotel stop a guest whose key card expired?

The door checks the card, not the front desk. Each new card carries a higher number. Once the door sees a card, it rejects every card with a lower number.

That number is a fencing token. The lock service issues a higher number with every grant. The holder sends it with every write. The protected resource keeps the highest number it accepted and rejects lower ones.

Map it back: Redis, ZooKeeper or etcd is the front desk, and the database is the door.

Who hands out the numbers, and who checks them?

Q21. Who issues the fencing token, and who checks it?

The lock service issues it at grant time. The protected database or service checks it at write time. Redis knowing the newest token is not enough, because Redis never sees the write.

Redis gives token 33 to server A and token 34 to server B. The database accepts 34 first, so the late write with 33 fails.

The token must come from the lock service as part of the same grant, and its counter must never go backwards. ZooKeeper (the zxid) and etcd (the key revision) meet both rules. Redis can issue one with INCR in the same script as SET NX, but a failover can lose increments, so that counter can go backwards.

So the database receives a number with each write. Where does it keep it?

Q22. How does the database store and check the token?

It keeps the highest accepted token on the protected row. Every write checks it in the WHERE clause:

-- server B holds token 34
UPDATE seats
SET    status = 'reserved', last_fencing_token = 34
WHERE  seat_id = 'A15' AND last_fencing_token <= 34;

-- server A wakes up with token 33
UPDATE seats
SET    status = 'reserved', last_fencing_token = 33
WHERE  seat_id = 'A15' AND last_fencing_token <= 33;
-- the row holds 34, so this matches zero rows

Use <=, so that one holder can write more than once with the same token.

But what if server A wakes up before server B writes anything?

Q23. Can server A still write after its lock expired?

Yes, until a newer token reaches the database. The rule “reject anything lower than the highest seen” stops an old write from landing after a newer one. It does not stop an old write that arrives first.

Server B can close that window. Right after it gets token 34, it writes the token to the row before it starts any work. From that moment the database rejects 33. Server B has fenced server A out.

In the top case the stale write lands because it arrives first. In the bottom case server B fences first, so it cannot.

Server A's lock expired at 10 seconds. Can the database reject it right then, not only after server B writes?

Q24. Can the database reject a write the moment its lock expires?

Yes, with a live check. At every write, the database or service asks the lock service whether the token is still current, and rejects the write if it is not.

This costs something. Every protected write now waits on the lock service, and writes stop when the lock service is down. A small gap also remains between that call and the commit, the same check-then-act gap as Q11.

So the usual choice is the local rule from Q22, “reject anything lower than the highest seen,” with the new holder fencing first as in Q23. The database enforces it without calling anyone.

Both reject token 33. The live check pays for that with a dependency on every write.

So far the damage is abstract. When does a stale write actually hurt?

Q25. When does a double grant corrupt data?

When the stale write overwrites or conflicts with newer work, and nothing later corrects it. Two examples:

  • An account balance. Server A reads a balance of 100 and pauses. Server B gets the lock, adds a deposit of 50 and writes 150. Server A wakes up and writes 100 minus its debit of 30, which is 70. The deposit is gone.
  • A shared device. Server A's lock expired, but it still sends “start job A” while server B sends “start job B.” The device gets two conflicting commands.

A seat sale has a final conditional write that catches this. A plain balance update does not.

A seat hold has the same double grant. Why is it not a problem there?

Q26. Why is Redis still fine for a seat hold?

The Redis lock is not the final authority. The final sale is a conditional write in the database (WHERE status = 'available'), so only one sale of A15 can succeed. A rare double grant becomes a UX glitch, not corrupt data.

But if the conditional write is the real guard, why have a lock at all?

Q27. Why not use only the conditional write?

The two do different jobs. The conditional write keeps the data correct. The hold tells user 456 “unavailable” at once, so user 456 does not type card details and then fail at the last step.

Layer 1 can be wrong for a moment. Layer 2 cannot, because only one conditional write can match.

So when is the glitch not acceptable?

Q28. When is a plain TTL lock not enough?

A plain TTL lock is enough only when two things are true. Every write it protects checks its own condition in the same atomic step, as in Q12 and Q26. And the holder does nothing else that you cannot undo.

It is not enough in these cases:

  • The write has no condition. In Q25, SET balance = 70 checks nothing. SET balance = 70 WHERE balance = 100 would match zero rows and save the deposit.
  • The holder has other side effects, such as a card charge, an email, an outside API call or a device command.
  • The holder writes several rows, and only the last write checks anything.

Then each write needs its own condition, or the resource must check fencing tokens. A stronger coordinator also helps, as Part 4 shows.

A conditional write protects the rule, not the owner. In the double-grant window, stale user 123 can still win the seat. The data stays correct, but the wrong user gets it.

Part 4: ZooKeeper and etcd

The usual stronger coordinators are ZooKeeper and etcd.

Q29. Do ZooKeeper or etcd fix the paused-server problem?

No. Their locks are cooperative too (Q19). A ZooKeeper lock is an ephemeral znode tied to the client's session. If the client freezes past the session timeout, ZooKeeper deletes the znode and gives the lock to the next client. The frozen client can wake up and act before it learns this.

Then why do people call them stronger?

Q30. What do they add over Redis?

Lock state that survives a failover, and a built-in fencing token that never goes backwards. The protected resource must still check that token.

That leaves three places to keep a lock.

Q31. Where should the lock live?

  • In the same database as the data, as a lease row or column. The final conditional write checks the lease and writes in one step, so it needs no fencing token. This is Part 2.
  • In Redis, for short, best-effort holds such as a checkout reservation. Keep a conditional write in the database as the final guard.
  • In ZooKeeper or etcd, when two owners would corrupt data and your team can run a coordination cluster. Check their fencing tokens at the resource.

A lease in the database needs no token. Why would anyone move it to Redis?

Q32. Why not always keep the lease in the database?

Speed and hotspots. Redis keeps keys in memory and answers much faster than a database write that must reach disk. A lease row is also one row that every contender updates. Under heavy contention, claims queue on that row's lock, and the load lands on the database that serves the rest of your app.

So keep the lease in the database while contention is moderate. Move it to Redis when claims are frequent, and keep the final conditional write in the database.

On the left, every claim becomes a database write on one row. On the right, only the final sale reaches the database.

Part 5: Which tool does a write need?

Step back. A distributed lock is one tool among several. How do I pick the right one for a write?

Q33. What does “a predicate on the row you write” mean?

A predicate is a true-or-false condition. In a conditional write, the WHERE clause holds a predicate on the same row that the write changes:

UPDATE seats SET status = 'sold'
WHERE  seat_id = 'A15' AND status = 'available';

This says “sell A15 only if A15 is still available.” The database checks the predicate and writes in one atomic step.

So if the row can answer the question, I need nothing else?

Q34. When is a conditional write enough?

When the database can decide from the current values of the row you write. Then a conditional write is the best default, and you need no lock.

And when the row cannot answer?

Q35. When must the check live in application code?

When one condition on one row cannot express the decision. Two common cases:

  • Several rows decide. To find four free seats side by side, the code reads the seat map and picks a block.
  • Outside information decides. The code picks the least-busy support agent, or calls another service first.

The rows can then change between the read and the write. That is the check-then-act gap from Q11 again, so the code needs a lock.

Which kind of lock?

Q36. Should I use a pessimistic or an optimistic lock?

It depends on how often requests collide.

  • Collisions are common: use a pessimistic lock (SELECT … FOR UPDATE). The rows stay unchanged while the code decides, and other requests wait.
  • Collisions are rare: use optimistic concurrency. Read a version number, decide, and write only if the version did not change. On zero rows, read again and retry.
-- read earlier: Maya has 3 open tickets, version 12
UPDATE agents
SET    open_tickets = open_tickets + 1, version = version + 1
WHERE  agent_id = 'maya' AND version = 12;
-- 0 rows updated: Maya's row changed, so read again and retry

The version number does the same job as a fencing token (Q20). The difference is that the database issues it, not a lock service.

Both kinds protect the rows I write. What if the rule covers rows I only read?

Q37. What is write skew?

An invariant is a rule that must always be true. For example, at least one engineer is always on call.

Alice and Bob are both on call. Each reads the table and sees two engineers on call. Each then sets only their own row to off call. The two writes touch different rows, so they never collide, and no row lock or version check fires. Both writes succeed, and nobody is on call. This is write skew.

At the top, both writes succeed because they touch different rows. At the bottom, both target one row, so Bob's write matches zero rows.

How do I stop it?

Q38. How do I protect a rule that spans rows?

Three ways:

  • Run the transaction at SERIALIZABLE isolation (Q39). The database aborts one of the two transactions.
  • Lock the rows you read with SELECT … FOR UPDATE. Bob then waits for Alice and sees only one engineer left. This works only for rows that already exist.
  • Move the rule into one row. Keep on_call_count on the team row, and step down with a conditional write. Both requests now write the same row, so they collide, and the predicate decides:
UPDATE teams SET on_call_count = on_call_count - 1
WHERE  team_id = 'payments' AND on_call_count > 1;

What does SERIALIZABLE look like in practice?

Q39. How do I run a transaction at SERIALIZABLE isolation?

Set the level when you begin the transaction:

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM on_call
WHERE  team_id = 'payments' AND is_active = true;
UPDATE on_call SET is_active = false WHERE engineer_id = 'alice';
COMMIT;

The database detects transactions whose combined result could not happen one at a time. It aborts one of them with a serialization error. Your code must retry that transaction, and the retry sees the other transaction's change.

Every tool so far lives inside one short transaction. What if the hold must outlive it?

Q40. When do I need a distributed lock?

When exclusive access must outlive one short transaction, because the protected work includes a wait, several steps or an outside call. A seat hold during checkout is one case. Others are:

  • one worker runs a scheduled job,
  • one server generates the monthly report,
  • a delivery driver stays reserved while you wait for a reply.

Parts 2 to 4 cover how to build one.

That is a lot of tools. How do I remember the order?

Q41. What is the whole decision, from top to bottom?

Climb the ladder and stop at the first rung that fits. The mnemonic is “Row answers. App locks. Span serializes. Time fences.”

  1. Row answers. The row you write can decide, so use a conditional write.
  2. App locks. Your code must decide, so use a lock. Hot rows: hold (pessimistic). Cold rows: check (optimistic).
  3. Span serializes. The rule spans rows that never collide, so use SERIALIZABLE, or move the rule into one row.
  4. Time fences. The hold outlives a transaction, so use a distributed lock and fence the final write.

Each rung down handles a harder case, and costs more.

Part 6: The whole chain

Q42. Can I say all of this as one chain?

  1. A pessimistic lock is held by a transaction, so it ends when the transaction ends.
  2. A checkout lasts minutes, so the hold cannot live in a transaction. It must be written as data.
  3. A written lock can outlive its owner's turn. The owner can pause, the lock can expire, and the owner does not know.
  4. Checking the lock before writing does not help, because the check and the write are two steps.
  5. So the write itself must check. When the lock and the data share a database, one conditional UPDATE does this.
  6. When the lock lives in Redis, ZooKeeper or etcd, the database cannot see it, and every distributed lock is cooperative. So each write must carry a fencing token from the lock service, and the database must reject old tokens.
  7. The usual rule, “reject anything lower than the highest seen,” orders writes but cannot see expiry. So the new holder writes its token first. A live check with the lock service is stricter but slower.
  8. A seat hold can skip tokens, because the final sale is already a conditional write. Use tokens when a stale write would do lasting damage.
  9. Keep the lease in the database while you can. Move it to Redis for speed or heavy contention, or to ZooKeeper or etcd when two owners would corrupt data.
  10. Before you reach for any lock, climb the ladder from Q41: row answers, app locks, span serializes, time fences.
