Locks held vs. locks written

2026-11-18

Read this top to bottom. Each answer raises the next question.

Part 1: Holding a lock

Two users click seat A15 at the same moment. Only one of them can get it.

Q1. What is the difference between a pessimistic lock and a distributed lock?

A connection holds a pessimistic lock. A distributed lock is a value written to shared storage.

A held lock ends when its holder ends: at commit, at rollback, or when the connection drops. A written lock ends at its expiry time or when code deletes it.

That is abstract. I need a picture.

Q2. What does that look like in real life?

A pessimistic lock is a guest in a chair at a restaurant table. Other guests wait in line at the door until that guest leaves. A distributed lock is a reservation card on the table. The guest can leave, and the card keeps the table.

The guest in the chair is the held lock. The card is the written lock.

In the picture, other guests wait at the door. Does a database really make them wait?

Q3. What happens when a second transaction wants a locked row?

It waits. Transaction A holds A15 with SELECT … FOR UPDATE. Transaction B runs the same query and blocks in the lock-wait queue. When A commits or rolls back, B gets the lock and reads the row as A left it.

Waiting forever sounds bad.

Q4. Does B ever get an error instead?

Yes, in three cases:

  • NOWAIT: the query fails at once if the row is locked.
  • Lock timeout: PostgreSQL waits forever by default (lock_timeout = 0). MySQL InnoDB stops after innodb_lock_wait_timeout, 50 seconds by default.
  • Deadlock: the database aborts one transaction and sends it an error.

After an error, your code decides whether to retry or to show “unavailable.”

The top row is the normal path. The red boxes are the only ways B gets an error instead.

Do readers get stuck in that queue too?

Q5. Does a plain read wait?

No. A plain SELECT without FOR UPDATE does not wait in PostgreSQL or InnoDB. It reads the last committed version. Only writes and locking reads wait.

A checkout takes up to ten minutes. Why not keep the row lock for the whole checkout?

Q6. What breaks if a transaction stays open for 10 minutes?

Four things:

  • Every other request for A15 waits up to ten minutes. Each waiter is also an open transaction.
  • Each open transaction pins one database connection. With a pool of 50, 50 users in checkout use every connection.
  • The user's “Pay now” click can reach a different app server. That server cannot continue the transaction.
  • An old open transaction stops PostgreSQL's vacuum from removing old row versions, and grows InnoDB's undo history.

If the app server hangs instead of crashing, its connection still looks alive. The lock stays until something closes the connection.

Part 2: Writing the lock as data

So the hold must outlive the transaction. Where can it live?

Q7. How do I hold a seat for 10 minutes without an open transaction?

Write the hold as data and commit at once:

-- 12:00: user 123 claims A15
UPDATE seats
SET    reserved_by    = 'user123',
       reserved_until = now() + interval '10 minutes'
WHERE  seat_id = 'A15'
  AND  status  = 'available'
  AND  (reserved_until IS NULL OR reserved_until < now());
-- 1 row updated:  user 123 owns the hold
-- 0 rows updated: another user owns it, so show "unavailable"

The transaction lasts milliseconds. After the commit, only a row remains. It says user123 owns A15 until 12:10.

No transaction is open now. What keeps the hold alive?

Q8. Why does the hold survive an app server crash?

No process holds it. It is a committed row that every app server can read. Only its expiry time or a delete ends it.

And the user who comes second?

Q9. What does user 456 see now?

The same UPDATE matches zero rows and returns in milliseconds. User 456 sees “unavailable” at once, without a queue. After 12:10 the same statement succeeds, and no cleanup job is necessary.

With the held lock, user 456 waits up to ten minutes. With the written lock, user 456 gets an answer in milliseconds.

Why the name “distributed”?

Q10. What makes this lock distributed?

It lives in shared storage that all app servers use, and no single process owns it. Redis does the same with SET seat:A15 user123 NX PX 600000. That command sets the key only if it is absent and deletes it after ten minutes.

A held lock always knows its owner. Does a written one?

Q11. What can go wrong with a lock written as data?

Two things:

  • It is advisory. It protects nothing unless every code path checks it.
  • Its holder can be stale. User 123 can click Pay at 12:11, after the hold expired and user 456 claimed the seat.

So user 123's server thinks it owns A15, but it does not.

Q12. How do I stop a stale holder from booking?

Check ownership again in the final write:

-- user 123 completes checkout
UPDATE seats
SET    status = 'booked', booked_by = 'user123'
WHERE  seat_id = 'A15'
  AND  reserved_by    = 'user123'
  AND  reserved_until > now();
-- 0 rows updated: the hold is lost, so do not confirm the booking

Without this check, two users can book the same seat. Use the database clock (now()) so clock differences between app servers cannot change the result.

Payment happens in a different system.

Q13. When do I charge the card?

Only after you confirm or extend the hold. Make the charge refundable, because the payment provider and the database cannot commit together.

Two users can still click in the same millisecond.

Q14. Who wins if two users claim A15 at the same moment?

The claiming UPDATE takes a short row lock, and that lock puts the two claims in order. The second UPDATE waits a few milliseconds. Then it checks the WHERE clause again and matches zero rows.

Read it top to bottom. The row lock lasts only from the claim to the commit.

So the two kinds of lock are not rivals.

Q15. How do the two locks fit together?

Every distributed lock is written under a short pessimistic lock. Hold a lock for milliseconds to make a decision atomic. Write a lock as data to keep ownership for minutes.

Part 3: Redis locks

Many teams keep holds in Redis. People say Redis locks are unsafe. Why?

Q16. Why do people push back on Redis TTL locks?

A TTL lock can have two owners for a short time. Server A works for user 123 and server B works for user 456.

Server A gets the lock with SET lock:A15 server-a NX PX 10000. NX sets the key only if it is absent. PX sets the TTL (time to live) to 10 seconds. Then server A freezes, for example in a long GC pause. Redis deletes the key and gives the lock to server B. Server A wakes up and still writes.

Server A freezes at 3 seconds. Redis deletes the key at 10 seconds and gives the lock to server B at 11 seconds. Server A wakes up at 17 seconds and still writes.

Did Redis do something wrong?

Q17. Is the expiry a Redis bug?

No. The expiry proves that Redis stopped listing server A as the owner. It does not prove that server A stopped working.

Is the pause the only risk?

Q18. Can Redis lose a lock some other way?

Yes, on failover. Redis copies data to replicas asynchronously. If the primary fails before it copies a new lock key, the promoted replica does not have the key, and another client can get the same lock.

Redis knows that server B owns the lock now. Why doesn't Redis block server A?

Q19. Why can't Redis stop the stale write?

Redis sees only the commands that acquire, renew and release the key. Server A sends its UPDATE straight to the database. Redis is not on that path.

The red path never passes through Redis. That is the gap a fencing token closes.

Then something on the write path must catch it.

Q20. Who must reject the stale write?

The database. It needs evidence that the write is stale, and a fencing token is that evidence.

What does that evidence look like?

Q21. What is a fencing token?

A number that increases with every lock grant. The holder sends its token with every write. The database keeps the highest token it accepted and rejects any lower one.

Redis gives token 33 to server A and token 34 to server B. The database accepts 34 first, so the late write with 33 fails.

What if server A sends the write without its token?

Q22. Does the token have to travel with the write?

Yes. Without a token, the database has nothing to compare. Server A's stale write can then overwrite server B's valid work.

Where do I get such a number?

Q23. Where do fencing tokens come from?

Plain Redis SET NX gives no such number. ZooKeeper (the zxid) and etcd (the key revision) give one with each lock. The reserved_by check in Q12 does the same job inside the database.

If Redis can give one lock to two servers, why does anyone use it for ticket holds?

Q24. Why is Redis still fine for a seat hold?

The Redis lock is not the final authority. The final sale is a conditional write in the database, so only one sale of A15 can succeed. A rare double grant becomes a UX glitch, not corrupt data.

But if the conditional write is the real guard, why have a lock at all?

Q25. Why not use only the conditional write?

The two do different jobs. The conditional write keeps the data correct. The hold tells user 456 “unavailable” at once, so user 456 does not type card details and then fail at the last step.

Layer 1 can be wrong for a moment. Layer 2 cannot, because only one conditional write can match.

When is “a UX glitch” not acceptable?

Q26. When is a plain TTL lock not enough?

When two owners could do damage that you cannot undo, such as moving money twice or sending conflicting commands to hardware. Then add fencing tokens or use a stronger coordinator.

Part 4: ZooKeeper

The usual stronger coordinator is ZooKeeper.

Q27. Does ZooKeeper fix the paused-server problem?

No. A ZooKeeper lock is an ephemeral znode tied to the client's session. If the client freezes past the session timeout, ZooKeeper deletes the znode and gives the lock to the next client. The frozen client can wake up and act before it learns this.

Then why do people call it stronger?

Q28. What does ZooKeeper add over Redis?

Lock state that survives a failover, and a built-in fencing token. The protected resource must still check that token.

So which one do I pick?

Q29. Redis or ZooKeeper?

Redis for short, best-effort holds such as a checkout reservation. ZooKeeper when two owners would corrupt data and your team can run a coordination cluster.
