Q1Proxy bottleneck

A video site still proxies every upload along the path in the figure. At peak, 400 clients are each sending a 2 GB file at a steady 25 Mbps. Counting file bytes only, what combined network throughput (inbound plus outbound) must the app-server tier sustain today, and what would it be after a switch to presigned direct uploads?

Options for question 1

Solution

Answer: C

Inbound on L2: 400 × 25 Mbps = 10 Gbps. A proxy is a pipe, so every byte that arrives must also leave on L3: another 10 Gbps outbound, 20 Gbps in all. After the switch the server answers one small request per upload and never touches file bytes, so the figure falls to roughly zero.

The 2 GB size is a distractor. It decides how long each transfer lasts, not how fast bytes flow. Option B is the usual slip: counting one direction only.

Q2Presigned URLs

A server issued this upload URL at 00:00:00 UTC for an HTTP PUT. The bucket has no extra policy conditions. Which request does the storage service accept?

https://media.s3.amazonaws.com/uploads/user123/video.mp4
  ?X-Amz-Algorithm=AWS4-HMAC-SHA256
  &X-Amz-Date=20240115T000000Z
  &X-Amz-Expires=900
  &X-Amz-SignedHeaders=host
  &X-Amz-Signature=b2754f5b1c9d…
Options for question 2

Solution

Answer: D

X-Amz-Expires=900 is 900 seconds, so the URL dies at 00:15:00 and A is 30 seconds late. The signature is a hash of the request details (method, path, expiry) and the secret key. Change the method (B) or the path (C) and the hash that the storage service recomputes no longer matches.

Nothing in the signature ties the URL to a device, a user or an address, so whoever holds it can use it until it expires. A presigned URL is a bearer token: keep its lifetime short and its scope narrow.

Q3Presigned URLs

A server signs with temporary credentials that expire 10 minutes from now. It creates a presigned PUT URL with a 60-minute expiry. The client starts its upload 25 minutes later. What happens?

Options for question 3

Solution

Answer: B

Validating a presigned URL means recomputing the signature with the storage service’s copy of the credentials that signed it. Once those credentials have expired or been revoked there is nothing valid to check against, so the request fails even though the URL’s expiry is still in the future. The effective lifetime is the shorter of the two.

This goes one step beyond the article, but it follows from how validation works, and AWS documents it for URLs signed with temporary credentials. Two practical consequences: sign with credentials that will outlive the URLs you hand out, and remember that revoking the signing credentials switches off every URL they produced.

Q4Resumable uploads

A 5 GiB file (1 GiB = 230 bytes) goes up at a steady 100 Mbps (1 Mbps = 106 bits per second) as a multipart upload with 64 MiB parts, sent one at a time, in order. The connection drops when exactly 99% of the bytes have been sent (figure). After reconnecting, how much upload time is still needed, and how long would a fresh single-request upload take?

Options for question 4

Solution

Answer: C

The file is 5 × 1,024 ÷ 64 = 80 parts. At 99%, 79.2 parts’ worth of bytes have left the client: parts 1 to 79 are complete and part 80 was cut off a fifth of the way in. A part either completes or it does not, so that fifth is thrown away. The client asks the storage service which parts it holds, then sends all of part 80 again: 64 × 220 × 8 bits at 108 bits per second is about 5.4 s.

A single PUT has no such memory and starts from byte zero: 5 × 230 × 8 ÷ 108 ≈ 429.5 s, a little over seven minutes.

B assumes only the missing 1% is re-sent (51.2 MiB, 4.3 s). D slips decimal gigabytes into a question stated in binary units.

Q5Range requests

A client pulls a 25 MiB object through a CDN in 10 MiB ranges. Its first request carries Range: bytes=0-10485759. Which header does the third request carry, and what Content-Length comes back?

Options for question 5

Solution

Answer: A

Byte ranges count from zero and include both ends, which is why the first 10 MiB (10,485,760 bytes) is written 0 to 10485759. The second range is 10485760 to 20971519, so the third starts at 20971520. The object has 25 × 220 = 26,214,400 bytes, so its last byte is number 26214399 and the final range holds 5,242,880 bytes.

B and D ask for bytes beyond the end. A server answers such a request with whatever exists, so the body would still be 5,242,880 bytes, not the lengths claimed. C skips byte 20971520 and corrupts the reassembled file.

Q6State sync

Presigned URLs in this system expire after 15 minutes. A row is written with status pending when the URL is issued, and a storage event normally flips it to completed. A reconciliation job runs now and finds the two rows in the figure. What should it do?

Options for question 6

Solution

Answer: C

Row X: the object exists, so the upload happened and its event was lost or is badly delayed. The bucket is the authority on what exists, so the job marks the row completed. B confuses an expired URL with a failed upload. D waits for an event that may never come, which is the very gap the job exists to close.

Row Y: there is no object yet, but the URL is good for another 11 minutes and the client may be in the middle of sending. Failing the row now (A, D) would throw away a healthy upload. A row should be failed only when the object is missing and enough time has passed that no upload can still be in flight: the URL’s lifetime, plus an allowance for a transfer that began just before it ran out.

Q7CDN signed URLs

The figure shows who signs and who checks in the two standard schemes, with the key material labeled K1 to K4. An attacker dumps the memory of one CDN edge node and obtains K4. Which statement is correct?

Options for question 7

Solution

Answer: B

The two schemes differ in exactly this respect. For the bucket, K1 and K2 are the same secret: the storage service validates by recomputing the hash with its own copy. For the CDN, K3 is a private key that stays on your servers, and K4 is the matching public key, copied to every edge so that each can verify on the spot with no call to your servers or to the origin.

A public key cannot produce signatures, which is what makes it safe to spread across hundreds of locations (A). It has nothing to do with the storage secret (C). The expiry is part of what was signed, so it cannot be edited afterward (D). The attacker can still read whatever that edge has cached, which is bad, but far smaller than a leaked signing key.

Q8Lifecycle rules

A lifecycle rule aborts incomplete multipart uploads two days after they begin. A user starts a 50 GB upload on Friday evening, pauses it at 60%, and resumes on the following Wednesday. What should the client expect?

Options for question 8

Solution

Answer: D

More than four days have passed, so the rule has aborted the upload and deleted its parts. Listing parts for that upload ID now fails and there is nothing left to resume (A). Completion cannot run on an aborted upload (B), and parts never add up to a readable partial object (C).

The rule exists because abandoned parts are billed like any other storage. Its window is also the longest pause the product can survive. One or two days is a trade between cleanup cost and resumability; a product that promises “pick it up next week” needs a longer window, or its own way of remembering what was sent.

Q9Cost

A service starts 50,000 multipart uploads a day, averaging 2 GB each. 4% of them are abandoned, on average half-way through. Storage costs $0.023 per GB per month. What is the monthly storage charge for abandoned parts (i) 30 days after launch with no lifecycle rule, and (ii) in steady state with a rule that aborts incomplete uploads after 2 days?

Options for question 9

Solution

Answer: A

4% of 50,000 is 2,000 abandoned uploads a day, each leaving half of 2 GB behind: 2,000 GB a day.

(i) After 30 days, 60,000 GB is sitting in the bucket: 60,000 × $0.023 = $1,380 a month, and every further day adds another $46 to the monthly bill. (ii) With the rule, about two days of leftovers exist at any time: 4,000 GB, or $92 a month, and it stays there.

B forgets that the uploads stopped half-way. C prices a single day’s leftovers. D gets the first number but misses that the bill grows without limit, and that the rule caps the cost without removing it.

Q10Downloads

A user’s line carries 120 Mbps in total, but the server limits each connection to 25 Mbps (figure). The user downloads a 6 GB file (1 GB = 8,000 megabits). How long does it take over one connection, and over six parallel ranged connections?

Options for question 10

Solution

Answer: D

6 GB is 48,000 megabits. One connection is held to 25 Mbps: 48,000 ÷ 25 = 1,920 s, or 32 minutes. Six connections could carry 150 Mbps between them, but the line tops out at 120 Mbps, so the download takes 48,000 ÷ 120 = 400 s.

That is 4.8 times faster, not 6 times (A). Parallel ranges help only while the per-connection limit is what holds you back. Once the user’s own bandwidth is the limit, extra connections add nothing: five connections already saturate this line, and the sixth changes nothing. Most users are limited by total bandwidth, which is why this trick is rarely worth its complexity.

Q11Presigned URLs

Which statements about presigned upload URLs are correct?

Options for question 11 (choose one or more)

Solution

Answer: B, C, D

B: signing is local arithmetic on the request details and your secret. The storage service first hears of the URL when someone uses it, and validates by recomputing the same hash. That is also why A is false: there is no registry of issued URLs.

C: conditions are baked into the signature, so a URL issued for a 5 MB image is refused for a 500 MB video. D: the URL is the credential, which is exactly why those conditions and a short expiry matter.

Q12State sync

After a direct upload, the client calls POST /uploads/{id}/complete and the server sets the row to completed without asking storage. Which outcomes are possible?

Options for question 12 (choose one or more)

Solution

Answer: A, C, D

A: a dishonest or buggy client can call the endpoint without uploading anything, and the call can also simply win a race with the upload. D is what the user then sees. C: the client crashes, or its network drops, after the upload and before the call. If the row is created only on that call, the object has no row at all and is orphaned.

B is not a consequence of trusting the client. Objects are written whole, and server-generated keys keep one upload from colliding with another.

Q13Storage events

In the design in the figure, the bucket publishes an event when an object is created, a worker updates the row, and a periodic job double-checks rows stuck in pending. Which statements are correct?

Options for question 13 (choose one or more)

Solution

Answer: A, B, D

A: the key is the join between the two systems. B: write the update as “set to completed if still pending”, which is harmless to repeat. D: with a job that runs every N minutes and inspects rows older than T, a lost event leaves a row wrong for roughly T + N at worst.

C is the trap. Events are the fast path, not a guarantee: network trouble, outages and processing errors can delay or drop them. The job is what turns “usually consistent” into “eventually consistent, within a known bound”.

Q14Abuse prevention

Uploads land in a quarantine bucket, pass through scanning and validation, and only then move to the bucket that is served to users (figure). Which statements are correct?

Options for question 14 (choose one or more)

Solution

Answer: A, B, C

A is the core idea: do not let users reach what they have just uploaded. Detection can then be slow and thorough instead of real-time. B protects the bill and belongs on every upload URL. C is a side benefit of the same delay.

D confuses a label with the contents. The storage service checks that the header matches what was signed; it does not open the file. An executable sent with an image content type passes that check, which is why file-type validation sits in the pipeline.

Q15Downloads

Which statements about fast downloads of large files are correct?

Options for question 15 (choose one or more)

Solution

Answer: A, C, D

A and D go together: ranges are what make a download resumable, and browsers and download managers use them automatically, provided the signed URL does not rule out the requests they send. C is the condition under which splitting a file across four to six connections helps (compare Q10).

B mistakes latency for throughput. A CDN removes distance, turning roughly 200 ms per request into a few milliseconds, which transforms a page made of thousands of small files. It does not widen the user’s line: 5 GB at 50 Mbps is 800 seconds wherever the bytes come from.

Q16Metadata

Which practices for tying metadata to direct uploads are sound?

Options for question 16 (choose one or more)

Solution

Answer: B, D

B gives you a record before the object exists, so nothing lands in the bucket without a row pointing at it, and the storage event has something to update. D makes keys unique and regular, and the event hands the key back to you.

A invites overwrites and worse: a client that picks its own key can aim at someone else’s object. C does not work as a query surface. S3, for example, allows ten tags per object, and “every PDF that user X uploaded last week” would mean inspecting objects one by one.

Q17Resumable uploads

Which statements about chunked uploads are correct?

Options for question 17 (choose one or more)

Solution

Answer: A, B, D

A: completion is the step that assembles parts into an object; skip it and you pay for bytes nobody can read, which is what lifecycle rules clean up. B: the storage service keeps the list under the upload’s session identifier (the upload ID on S3, the session URL on Google Cloud), so a client that lost its own notes can still recover. D: the idea is the same on every cloud but the URL structure is not.

C: once completion succeeds the parts no longer exist as separate things. Changing the object means uploading it again.

Q18When to proxy

For which of these should the bytes still pass through your own servers?

Options for question 18 (choose one or more)

Solution

Answer: B, C, D

B has to see the bytes as they arrive in order to refuse them synchronously. D must be inspected before storage, so it cannot go to the bucket first. C is too small to earn an extra round trip; an ordinary endpoint is simpler and faster. A is the textbook case for direct upload.

Notice that B is over 10 MB and still belongs on the server. The size rule tells you when proxying starts to hurt, not when it stops being necessary. When you do proxy something large, stream it through in chunks.

Q19Dropbox

A file-sync product wants faster transfers and tight access control. Which statements are correct?

Options for question 19 (choose one or more)

Solution

Answer: B, C

B: encrypted data looks random, and random data does not compress. C: every boundary after the insert now cuts the data in a different place, so delta sync ends up re-sending almost the whole file. Content-defined chunking, which places boundaries with a rolling hash over the content, confines the change to the chunks around the edit.

A: media formats are already compressed. A PNG or an MP4 shrinks by a few percent at best, so the time is wasted; text is where compression pays. D: a signed URL is a bearer token. A short expiry narrows the window in which a leaked link works; it does not close it. Binding the URL to an address, or requiring a session cookie as well, goes further.

Q20YouTube

Which statements about storing and streaming video are correct?

Options for question 20 (choose one or more)

Solution

Answer: B, C, D

B, C and D are the three steps from a bad design to a good one: transcode into several formats, cut every format into segments a few seconds long, and publish manifests so that a player can find any segment in any format.

A puts the intelligence in the wrong place. The player reads the manifest, watches its own throughput, and asks for the next segment in whichever format it can afford. The server side just serves files, which is why the whole thing sits comfortably behind a CDN.

Q21Instagram

A photo-sharing app uploads originals straight to a bucket, lets storage events trigger the workers that make thumbnails, and serves feed images through a CDN with signed URLs. Which statements are correct?

Options for question 21 (choose one or more)

Solution

Answer: B, C

B: a signed URL is valid only until its expiry, so a copy embedded elsewhere soon breaks, while your own app keeps issuing fresh ones. C: the request that creates the post returns as soon as the row and the upload URL exist. The heavy work starts later, from the storage event, and runs on separate workers.

A sounds plausible and is wrong. The edge validates the signature first, then looks the object up in its cache by path. The signature parameters are not part of what identifies the cached object, so one cached copy serves every viewer who arrives with a valid URL. That is how CloudFront treats its own signed URLs, a detail from its documentation, not from the article. D skips the processing step: until the workers have produced the variants and marked the post ready, followers would be asking for images that do not exist yet.

Q22Presigned URLs
Assertion
On S3, a 5 GB upload that starts one minute before its presigned URL expires can still finish successfully several minutes after the expiry time.
Reason
The storage service checks the signature and the expiry when the request begins, not continuously while the body is being transferred.
Options for question 22

Solution

Answer: A

Both are true, and the Reason is why. The expiry limits when a request may start; a transfer already under way runs to completion. This is documented S3 behavior and goes a little beyond the article.

Two things follow. A row cannot be declared failed the instant its URL expires, because an upload may have started just in time (compare Q6). And if that connection drops, the retry is a new request and will be refused, which is one more argument for parts with fresh URLs over one long PUT.

Q23CDN signed URLs
Assertion
A CDN edge can accept or reject a signed URL without contacting your servers or the origin bucket.
Reason
Each edge location holds a copy of your secret access key and recomputes the same hash that the storage service would.
Options for question 23

Solution

Answer: C

The Assertion is true: edges validate on the spot. The Reason is false. CDN signed URLs use a key pair. You sign with the private key, and the edge verifies with the public key that you registered with the CDN. Your storage secret never goes near an edge.

Recomputing a hash with a shared secret is how the bucket validates its own presigned URLs. That is the other scheme (compare Q7).

Q24Resumable uploads
Assertion
After a multipart upload has been completed, a client can repair a damaged region by uploading just the affected part number again.
Reason
Once completion succeeds, the parts are assembled into a single object and no longer exist as separate pieces.
Options for question 24

Solution

Answer: D

The Reason is true, and it is exactly why the Assertion is false. After completion there is one object and no open upload to add parts to. Repairing it means uploading a new object under that key.

Part-level retries are available only while the upload is still open, and that is where integrity checks belong: compare the checksum returned for each part before you ask the storage service to assemble them.

Q25Resumable uploads
Assertion
Chunked uploads make an accurate progress bar easy to build.
Reason
A chunked upload can resume from the first missing part instead of starting again.
Options for question 25

Solution

Answer: B

Both statements are true, but one does not explain the other. Progress is easy because every finished part is a known fraction of the file, so the client can do the arithmetic as acknowledgements come in. Resuming works for a different reason: the storage service remembers which parts it holds for that upload.

One mechanism, two separate benefits. A design could have either without the other.

Q26Dropbox and YouTube
Assertion
In the Dropbox and YouTube designs, the backend cannot use bucket notifications to tick off individual chunks as they arrive.
Reason
For a multipart upload, the bucket emits one object-level notification when the upload is completed, and none for the individual parts.
Options for question 26

Solution

Answer: A

Both are true, and the Reason is the explanation. Chunk-level progress therefore has to be reported by the client. After each part it sends the part number and the ETag that S3 returned, and the server checks those against ListParts before recording the chunk as uploaded.

The single completion event is still useful. In the YouTube design it is the trigger that starts video processing.

Passage I: a photo-sharing app

Questions 30 to 32 refer to this passage.

A photo-sharing app with about 500 million daily users takes in about 100 million posts a day. Photos may be up to 8 MB and videos up to 4 GB. The team settles on the flow in the figure.

  1. The app calls POST /posts with the caption and media details. The Post Service writes a post row with status pending and returns upload credentials: a single presigned PUT URL for a photo, or, for a video, it opens a multipart upload and returns one presigned URL per part.
  2. The app uploads straight to the media bucket.
  3. When the object is finalized, the bucket emits an event to a queue.
  4. Media workers write resized variants back to the bucket, then mark the post ready.
  5. Feeds include only ready posts, and load media through a CDN using signed URLs.
Q30Instagram

Suppose every media byte were instead proxied through the Post Service, and the average post carried 5 MB of media. The average inbound rate that the service tier would have to absorb is closest to

Options for question 30

Solution

Answer: C

100 million posts × 5 MB is 5 × 1014 bytes a day. Divide by 86,400 seconds: about 5.8 × 109 bytes per second, which is 46 Gbps. B is the same number with the factor of 8 between bytes and bits left out.

That is the daily average. Peaks run higher, and a proxy must send every byte on again to the bucket. So although most photos here are under the 10 MB rule of thumb, the volume alone justifies direct upload. The rule of thumb describes when one file hurts; it says nothing about a hundred million of them.

Q31Instagram

A creator uploads a 4 GiB video in 16 MiB parts. Counting only network calls from the Post Service to the blob store, how many are needed before the app can start sending parts?

Options for question 31

Solution

Answer: B

One: the call that opens the multipart upload. The upload ID is issued by the storage service, so it cannot be produced locally. The part URLs can: 4 GiB ÷ 16 MiB = 256 parts, and each URL is a signature over the upload ID and a part number, computed in memory.

A assumes that everything about presigning is local; D assumes that nothing is. The completion call is a second request to the store, but it comes after the parts.

Q32Instagram

The product team wants to refuse videos longer than 60 minutes. Which approach fits this design?

Options for question 32

Solution

Answer: D

With direct upload the server never sees the bytes in flight, so nothing that depends on the content can be enforced during the upload. The signed conditions know only size and declared type, and size is not duration, since bitrates differ by an order of magnitude (A). A check in the app is easy to bypass; its value is in saving an honest user a wasted upload (B).

The enforceable place is step 4. No one can see the post until the workers mark it ready, so they can measure the real duration, fail the post and delete the object. C overreacts. Proxying is for data that must be refused before it is accepted; here it is enough to accept the bytes and decline to publish them.

Passage II: a file-sync client

Questions 33 to 35 refer to this passage.

A file-sync product must handle files as large as 50 GB. Its desktop client splits each file into chunks on the device and computes a fingerprint (a SHA-256 hash) for every chunk and for the whole file. It asks the File Service whether an upload with that file fingerprint is already in progress for this user. If so, it fetches the chunk statuses and carries on from there.

Otherwise the File Service opens a multipart upload, saves a metadata row with status uploading and a list of chunks, and returns one presigned URL per part. After each part succeeds, the client sends the part’s ETag to the service in a PATCH. The service confirms what the client reports against the storage service’s own list of parts before recording a chunk as uploaded. When every chunk is confirmed, the service makes the completion call, and only then marks the file uploaded.

Q33Dropbox

Suppose the storage service accepts at most 10,000 parts per upload, and every part except the last must be at least 5 MiB. For a 50 GiB file (1 GiB = 1,024 MiB), what is the smallest whole number of MiB per part that works?

Options for question 33

Solution

Answer: B

50 GiB is 51,200 MiB. Spread over at most 10,000 parts, each part must hold at least 5.12 MiB, so the smallest whole number is 6 MiB (8,534 parts). At 5 MiB the file needs 10,240 parts, and the upload fails when it reaches part 10,001, after roughly 48.8 GiB has already been sent.

“Chunks of 5 to 10 MB” and “files up to 50 GB” sit right on this edge. A client should derive its part size from the file size, not hard-code the minimum.

Q34Dropbox

Why does the File Service check the storage service’s list of parts, when it could (i) wait for a bucket notification per chunk, or (ii) simply believe the PATCH?

Options for question 34

Solution

Answer: A

(i) There is nothing to wait for: part uploads do not raise bucket events. (ii) The client’s report is good for a responsive progress bar, but it is only a claim. Accepting it unchecked lets a faulty or dishonest client put the metadata out of step with the bucket, a state that is painful to debug later. So the design takes the client’s word for display and the storage service’s word for truth. Trust, but verify.

The other options invent problems. ETags come back to the client in every part response, so they are hardly secret, and a status update keyed by chunk is naturally repeatable.

Q35Dropbox

A 1 GiB file has been synced in fixed 4 MiB chunks. The user inserts 100 bytes at the 6 MiB mark (figure). How many chunks must be uploaded if the client keeps fixed-size chunks, and how many with content-defined chunking? Assume that the content never repeats, and that content-defined boundaries line up again just after the edit.

Options for question 35

Solution

Answer: B

Before: 1,024 ÷ 4 = 256 chunks, numbered 0 to 255. After: the file is 100 bytes longer, so it has 257 chunks, the last holding just 100 bytes. Chunk 0 is untouched. Chunk 1 contains the insert. Every later chunk holds the old data shifted by 100 bytes, so its fingerprint is new. That makes 256 chunks to upload, which is nearly the whole file. A forgets the small new chunk at the end; C counts chunk 0.

Content-defined chunking chooses boundaries from the data itself, using a rolling hash. The boundaries after the edit move along with the data, the chunks between them are byte for byte what they were, and only the chunk or two around the insert change.

Passage III: a video platform

Questions 36 to 38 refer to this passage.

A video platform receives about a million uploads and serves about 100 million views a day. Originals can run to tens of gigabytes and arrive by multipart upload. When an upload is completed, the bucket emits a single object-created event that starts the workflow in the figure: split the original into segments a few seconds long; transcode every segment into every supported format, in parallel; write one media manifest per format, listing its segments, and one primary manifest, listing the formats; then mark the video ready.

A player fetches the primary manifest through a CDN, picks a format, and requests segments one after another, changing format as its measured throughput changes.

Q36YouTube

A 10-minute video is cut into 4-second segments and offered in 5 formats. Leaving aside the original and any temporary files, how many objects does the workflow write?

Options for question 36

Solution

Answer: D

600 s ÷ 4 s = 150 segments per format, so 750 segment files across 5 formats. Add one media manifest per format (5) and one primary manifest: 756.

A viewer who watches the whole video in one format fetches the primary manifest, one media manifest and 150 segments. All of them can be served from the CDN, so a playback in progress need not touch your backend at all.

Q37YouTube

The formats and their bitrates are 240p at 0.4 Mbps, 480p at 1.0 Mbps, 720p at 2.5 Mbps and 1080p at 5.0 Mbps. Before each segment the player measures throughput (figure) and picks the highest format whose bitrate is no more than 80% of that measurement. Which formats does it choose for segments 1 to 5?

Options for question 37

Solution

Answer: C

Apply the 80% margin first: 8.0, 6.5, 3.0, 1.1 and 6.0 Mbps become budgets of 6.4, 5.2, 2.4, 0.88 and 4.8 Mbps.

Segments 1 and 2: 5.0 fits, so 1080p. Segment 3: 720p needs 2.5 and the budget is 2.4, so the player drops to 480p. Segment 4: 480p needs 1.0 against 0.88, so 240p. Segment 5: 1080p needs 5.0 against 4.8, so 720p.

A is what you get without the margin. The choice is made by the player, segment by segment, and that is possible only because every format was cut at the same segment boundaries and indexed in a manifest. The five segments come to 4 s × (5 + 5 + 1 + 0.4 + 2.5) Mbps = 55.6 megabits, about 7 MB.

Q38YouTube

A viewer on a 100 Mbps connection opens a 10 GB video (1 GB = 8,000 megabits) whose 1080p format runs at 5 Mbps. Ignoring manifest fetches and latency, how long is it before playback can begin if (i) the whole file must be downloaded first, and (ii) the player needs only the first 4-second segment?

Options for question 38

Solution

Answer: B

(i) 10 GB is 80,000 megabits; at 100 Mbps that is 800 s, a little over 13 minutes. (ii) One segment is 4 s × 5 Mbps = 20 megabits, which arrives in 0.2 s.

A leaves out the factor of 8 between bytes and bits, and D confuses minutes with seconds. C assumes that a 4-second segment takes 4 seconds to fetch. It would on a 5 Mbps line, but this one is twenty times faster, and the surplus is what lets the player buffer ahead. A failed request also costs one segment, not the whole download.
