Q1Two writes

The figure shows the article’s flow. The web server is killed after step 1 has committed and before step 2 begins. Nothing else has been added to the design. What state is the system in?

Options for question 1

Solution

Answer: C

Workers learn about jobs only from the queue (step 4), so a row with no message is invisible to them. The server died before step 3, so the client got an error or a timeout, not an ID. It will probably try again, which creates a second row unless the request carries an idempotency key.

A describes a design that would work, but it is not this one. D is what the opposite order risks: message first, row second.

The article says that during a queue outage jobs accumulate in the database as pending. That only helps if something later sweeps stale pending rows onto the queue. A periodic sweeper does it, and so does a transactional outbox. Neither is named in the article.

Remember Row first, then message. A crash between the two leaves an orphan you can see and sweep.

Q2Heartbeats

A worker sends a heartbeat every 10 seconds. The queue treats a worker as dead after 30 seconds of silence and makes its job available to others. Part-way through a job, the worker freezes for 40 seconds in a garbage-collection pause (figure), then wakes and carries on. What happens?

Options for question 2

Solution

Answer: D

The queue cannot see inside a worker. Thirty seconds of silence looks the same whether the process died or merely stopped responding, so at the 50-second mark the job becomes available and worker B starts it. Worker A then wakes with no idea any of this happened, and finishes too.

A queue has no power to kill a process (B). One timeout is one delivery attempt, not the three to five failures that send a job to the dead letter queue (C).

This is the false-alarm side of the heartbeat trade-off the article describes, and the reason it asks for the work itself to be idempotent.

Remember A timeout cannot tell dead from slow. Assume every job may run twice.

Q3Poison message

A Kafka consumer works through one partition in order and commits an offset only after the job at that offset succeeds. The job at offset 41 crashes the handler every time (figure). No retry or dead-letter logic has been written. What happens to offsets 42 and beyond?

Options for question 3

Solution

Answer: B

A consumer group keeps one committed offset per partition. Here it is stuck at 41, so whichever consumer is given the partition after a crash begins at 41 again. Nothing behind it can be reached without first moving past it. This is the article’s poison message taking workers down one after another, made worse by ordering.

SQS (a redrive policy) and RabbitMQ (a dead letter exchange) will set a message aside for you after N failures. A Kafka broker will not. The consumer has to catch the failure, publish the message to a retry or dead-letter topic after a few attempts, and commit past it.

That last point goes beyond the article, which names built-in dead-letter support only for SQS and RabbitMQ.

Remember SQS and RabbitMQ dead-letter for you. With Kafka, you write it yourself.

Q4Check, then act

The article’s submit_job looks the idempotency key up first, and creates the job only if the lookup finds nothing. A double-click sends two identical requests to two web servers 5 ms apart (figure). What can happen, and what is the smallest fix?

Options for question 4

Solution

Answer: A

Looking and then inserting is two steps, and another request can slip in between them. Both servers look, both see nothing, both insert.

The queue cannot help (C): it sees two different job IDs. A delay only moves the window (B). The database is the one place where both requests meet, so let it decide. Insert the key under a unique constraint; if the insert conflicts, read the row that won and return its job ID. An atomic set-if-absent in a cache does the same job.

The article’s code shows the idea, not the locking. This is where the Dealing with Contention pattern meets this one.

Remember Do not check and then insert. Insert, and let a unique constraint say no.

Q5Scaling signal

Each job makes one call to a partner API that allows your account 100 calls a second. Your 40 workers already use all 100. Queue depth has tripled in an hour, and worker CPU sits at 15% because the workers mostly wait on the network (figure). Which response is right?

Options for question 5

Solution

Answer: D

CPU says nothing here. These workers are idle while they wait, so a CPU policy never fires (A). Queue depth is the right alarm, which is the article’s point.

But the article’s remedy, more workers, assumes the workers are what is slow. Here they are not. A 41st worker only earns more rejections from the partner (B). Calling from the web tier removes the buffer and hands the limit straight to your users (C).

What is left is to drain at the allowed rate and decide what to do with the excess: tell users it will take longer, or refuse new jobs past a depth limit. If the backlog never drains, the real fix is a higher limit from the partner.

Remember Queue depth says you are behind. It does not say the workers are why.

Q6Worker hosting

Which workload is the best fit for serverless functions as the workers?

Options for question 6

Solution

Answer: A

Serverless earns its keep on spiky load. It scales to a thousand copies and back to none, and you pay only while code runs. A has that shape, and each job is far inside the limits.

B is steady, so there is nothing to scale away from, and always-on servers or containers cost less than paying per execution. C runs past the execution cap, which the article puts at 15 to 60 minutes depending on the provider. D pays a cold start whenever it scales up, and a 40-second one at that; it wants warm workers that keep the model loaded.

Remember Serverless for spiky and short. Servers or containers for steady, long, or slow to warm up.

Q7Ordering

Jobs for the same customer must run in the order they were submitted. Jobs for different customers should run in parallel. The queue is Kafka. Which setup gives both?

Options for question 7

Solution

Answer: C

Kafka’s ordering guarantee holds within a partition, as the article notes in passing. Messages with the same key go to the same partition, so keying by customer puts each customer’s jobs in one ordered lane, while different customers spread across lanes that are read in parallel.

A keeps order and gives up parallelism: within a group, a partition is read by one consumer, and the rest sit idle. B gives parallelism and scatters one customer’s jobs over partitions that have no order between them. D misreads the guarantee.

The keying rule is standard Kafka behavior, not something the article spells out. Its cost is that one very busy customer makes one very busy partition.

Remember Order lives inside a partition. The key picks the partition.

Q8Mixed workloads

Report jobs of unknown length start in the fast queue. Any job still running after 60 seconds is stopped and queued again on the slow queue (figure). For this to be safe, what must be true of a report job?

Options for question 8

Solution

Answer: B

Moving a job between queues is a retry by another name. The first run is cut off part-way, and a second run starts on the slow workers. Whatever the first run already did is still there: rows written, a half-built file, perhaps an email sent. So the job must be idempotent, or it must record checkpoints and resume from them.

A is backwards; the slow queue exists because the job will not finish in 60 seconds. C gives up fault tolerance for nothing. D is unrelated, and is the opposite of what the article recommends.

Remember Moving a job from fast to slow is a retry. Retries need idempotent jobs.

Q9Capacity

A site resizes a million images a day, about 12 a second on average. One resize keeps one worker busy for 10 seconds. The team runs 100 workers behind a durable queue with no depth limit. What happens over a normal day?

Options for question 9

Solution

Answer: D

A hundred workers at 10 seconds a job complete 10 jobs a second. About 12 arrive. The queue gains roughly two jobs every second, well over 100,000 by the end of the day, and the wait grows with it.

A queue evens out bursts: it lends you capacity now, and you pay it back when traffic drops. It cannot cover a shortfall that never ends (A). The article’s own arithmetic, 120 seconds of work arriving every second, says this load needs at least 120 workers at average traffic, and more at peak.

Remember A queue smooths bursts. It cannot fix arrivals that outrun the workers.

Q10Message contents

Following the article, a queue message holds only a job ID. A worker pulls a message, fetches the row, and finds that the user cancelled the job while it waited in the queue. What should the worker do, and what made that easy?

Options for question 10

Solution

Answer: C

The database row is the source of truth for the job. The message is only a reminder to go and look. Because the worker reads the row when it starts, it sees the job as it is now, not as it was when it was queued, and a cancelled job costs one cheap lookup.

Had the message carried the whole payload, the worker would be acting on a snapshot, and cancelling would mean finding and removing one message from the middle of a queue, which most queues cannot do. Small messages also stay under limits such as the 1 MB cap the article gives for SQS.

The dead letter queue is for jobs that keep failing (B). This one did not fail.

Remember The message says “go and look”. The row says what is true.

Q11Trade-offs

A 45-second PDF report is moved out of the request and onto async workers. Which statements are correct?

Options for question 11 (choose one or more)

Solution

Answer: B, C, D

A is the tempting one. The report still takes 45 seconds to build, plus whatever time it spends waiting in the queue, so the PDF arrives no sooner and possibly later.

What changes is who waits, and how. The request returns at once (B), the user is free to leave, and the work happens somewhere that can fail without hurting the API (D). The price is eventual consistency (C): accepted is not done, and the product needs a status to show in between.

Remember Async moves the wait off the request. It does not shrink the work.

Q12Failure isolation

In the article’s design the server writes the job row, then pushes the job ID to a durable queue. Which statements about failures are correct?

Options for question 12 (choose one or more)

Solution

Answer: A, B, D

A, B and D are the article’s claim that each part can fail on its own. Note the condition hidden in A, which Q1 is about.

C is the exception. The first step of accepting a job is the database write. Without it there is no row, no ID to return, and no key to check for duplicates, so new submissions fail. What the article says about a database outage concerns the workers: they retry their status updates until it recovers.

Remember The queue covers for workers that are down. The database is still on the accept path.

Q13Idempotent work

A job may be delivered more than once. Which of these worker steps are safe to repeat exactly as written?

Options for question 13 (choose one or more)

Solution

Answer: A, C

A sets a value; run it twice and the row is the same. C writes to a name derived from the job, so the second run overwrites the first with the same content.

B subtracts again every time it runs. D has a gap: a crash after the send and before the insert leaves no record, so the retry sends again. The article suggests checking first whether the email was already sent. That narrows the gap but cannot close it, because the send and the record live in two systems. The usual answer is to give the email provider an idempotency key derived from the job, so that the provider drops the repeat.

Remember Set, do not add. Name outputs after the job. Give side effects a key.

Q14Backpressure

On Black Friday jobs arrive at ten times the normal rate, and the workers cannot keep up. Which responses are sound?

Options for question 14 (choose one or more)

Solution

Answer: A, B, D

A is backpressure as the article defines it: refuse work you cannot do, instead of accepting it and failing later. B adds capacity, on the right signal. D is the mixed-workload fix applied by importance: separate queues protect the jobs that matter from the jobs that are merely numerous.

C treats the symptom. A queue that never refuses grows without limit, memory climbs, and jobs wait hours for results that nobody is still waiting for.

Remember When overloaded: shed, scale, separate. Never just stretch the queue.

Q15Heartbeats

Which statements about choosing a heartbeat interval or timeout are correct?

Options for question 15 (choose one or more)

Solution

Answer: A, B, C

A, B and C are the three sides of the trade in the article. Its advice is to take the longest interval your users can tolerate as extra delay, with 10 to 30 seconds as a starting point.

No setting achieves D. A timeout detects silence, not death (Q2), so any value short enough to be useful will sometimes fire on a live worker. Getting the effect of exactly once comes from idempotent work, not from the timer.

The same idea has three names: visibility timeout in SQS, heartbeat interval in RabbitMQ, session timeout in Kafka.

Remember Long timeout: slow recovery. Short timeout: false alarms. Neither gives exactly once.

Q16Dead letter queue

Which statements about dead letter queues are correct?

Options for question 16 (choose one or more)

Solution

Answer: B, C, D

A dead letter queue is a parking lot, not a retry loop (A). Jobs go there after three to five failures so that workers stop spending time on them, and they stay until a person looks.

B and C come straight from the article. D is why the threshold is not one: most failures are passing, and a few retries with some delay clear them. The dead letter queue is for what survives the retries.

Remember Retry what is passing. Park what persists. Alert on the parking lot.

Q18Job dependencies

A report needs three steps: fetch the data, build the PDF, send the email. Each worker queues the next step itself (figure). Which statements are correct?

Options for question 18 (choose one or more)

Solution

Answer: A, B, D

A is why the article’s example message carries a storage URL for the fetched data.

B and C are the two possible orders. Complete, then queue, can lose the chain: the step is recorded as done, so nothing retries it, and the next step was never queued. The article’s order, queue and then complete, cannot lose the chain. But a crash between the two means the step is retried and the next step is queued a second time. It trades a lost workflow for a possible duplicate, so the steps must be idempotent.

D is where chains run out. No single place shows where a workflow is stuck. An orchestrator gives you that, with retries per step, at the price of more machinery.

Remember Queue the next step, then mark done. A duplicate is survivable; a lost chain is not.

Q19Idempotency keys

A user clicks “Generate report” three times in two seconds. Which choices of idempotency key collapse the three clicks into one job?

Options for question 19 (choose one or more)

Solution

Answer: B, D

A key must be the same for requests that mean the same thing. A and C differ on every request, so they remove nothing.

B is one key per intention: every click and every network retry carries it. D is the article’s recipe. Rounding the time makes clicks inside the window agree, while a deliberate re-run later gets a new key. Including the parameters matters too; without them a different report requested a minute later would be swallowed as a duplicate.

D has an edge. Clicks at 11:59:59 and 12:00:01 fall in different windows and make two jobs. That is usually acceptable, and B does not have the problem. Whichever you choose, enforce it as in Q4.

Remember Same intention, same key. A key that changes on every request removes nothing.

Q21At least once
Assertion
A worker that finishes a job and dies before acknowledging the message causes the job to run again.
Reason
A message that is never acknowledged becomes available again when its timeout passes, and the queue cannot tell finished-but-silent from never-finished.
Options for question 21

Solution

Answer: A

Both are true, and the Reason is why. The acknowledgment is the only evidence the queue has that the work was done. Without it the queue must assume the worst and deliver again; assuming the best would lose jobs.

This is at-least-once delivery, and it is the second road to duplicates. The first was a live worker that looked dead (Q2). Here the worker really is dead, and the work really was finished.

Remember No acknowledgment, no proof. The queue will send it again.

Q22Autoscaling
Assertion
The article recommends that worker autoscaling be driven by CPU utilization.
Reason
By the time worker CPU is high, the queue has already backed up.
Options for question 22

Solution

Answer: D

The Reason is the article’s argument against the Assertion. CPU lags behind the problem, and for workers that mostly wait on the network it may never rise at all (Q5). Queue depth measures the thing you care about: work that is waiting.

Remember Scale workers on queue depth. CPU tells you late, or never.

Q23Redis
Assertion
A job queue built on Redis can lose jobs it had already accepted if the server crashes hard.
Reason
Redis has no way of writing its data to disk.
Options for question 23

Solution

Answer: C

The Assertion is true and the Reason is false. Redis does offer persistence. But it is memory-first: a write is acknowledged from memory and reaches disk a little later, so a hard crash can lose the most recent ones.

The article’s verdict is that Redis with BullMQ is simple and right for most uses, and that SQS or RabbitMQ is the choice when jobs must not be lost.

Remember Redis: memory first, disk a moment later. That moment is the risk.

Q24Chunking
Assertion
Cutting one five-hour fan-out job into thousands of small batch jobs shortens the wait for other jobs that share the queue.
Reason
When a small batch fails, only that batch is retried, not the batches that already succeeded.
Options for question 24

Solution

Answer: B

Both are true, but they are two separate benefits. The wait shrinks because a worker finishes a small batch quickly and can take someone else’s job next; nobody is stuck behind a five-hour job. That is the end of head-of-line blocking.

Cheaper retries are a second gain with a different cause: less work is lost when something fails.

Remember Small jobs: others do not wait, and failures cost less. Two wins, two reasons.

Q25ChatGPT
Assertion
For an LLM chat, returning a job ID and having the client poll until the whole answer is ready is a poor design, even though generating the answer is a long-running task.
Reason
What the user feels is the time to the first token, so partial output has to reach them while the rest is still being generated.
Options for question 25

Solution

Answer: A

Both are true, and the Reason explains the Assertion. The breakdown’s public requirements put it plainly: latency to the first token matters more than the time to finish.

The pattern still applies to the back half. Generation is queued, scheduled onto scarce GPU workers, and can be cancelled. But “we will notify you when it is ready” is replaced by a stream. Passage IV builds on this.

Remember Long-running does not always mean “come back later”. Sometimes it means “stream as you go”.

Passage I: a photo-sharing app

Questions 30 to 32 refer to this passage.

A photo-sharing app has about 500 million daily users and takes in about 100 million posts a day. Photos can be up to 8 MB and videos up to 4 GB. The team settles on the flow in the figure.

  1. POST /posts writes a post row with status processing and returns upload URLs. The app uploads the media straight to object storage.
  2. When the upload lands, an event from the bucket puts a job on the media queue.
  3. Media workers build the resized variants of a photo, or transcode a video into several resolutions. They then run a content-policy check and mark the post ready.
  4. Marking a post ready queues a fan-out job. Fan-out workers add the post ID to each follower’s precomputed feed, a sorted set in Redis. Accounts with more than 100,000 followers are skipped here; their posts are merged into feeds at read time.
Q30Instagram

A photo takes about two seconds to process. A 4 GB video can take more than an hour. Which layout suits steps 2 and 3?

Options for question 30

Solution

Answer: D

This is the mixed-workloads deep dive. In a single queue, photos wait behind videos (A): a burst of video uploads parks every free worker on a transcode, and two-second jobs queue for an hour. Separate queues let each kind be sized and scaled on its own numbers, and put video on hardware suited to it.

B is the synchronous design the pattern replaces. C fails on the long jobs: an hour-long transcode runs past the execution cap, though functions could serve the photo queue on its own.

Remember Different durations: different queues, different workers.

Q31Instagram

An account with 80,000 followers posts. How should the fan-out in step 4 be shaped?

Options for question 31

Solution

Answer: B

The article’s advice for a large job is to break it into smaller pieces, and its example is feed fan-out split into batches of followers. Batches run in parallel across workers, a failed batch is retried alone, and no worker is tied up for long (Q24).

With one big job (A, D), a crash at follower 79,000 means starting over or keeping a checkpoint, and a bigger machine changes neither. C puts a long task back into a request.

The write is idempotent without extra effort: adding a post ID that is already in a sorted set changes nothing, so a retried batch does no harm.

Remember A big fan-out is many small batches. Adding to a set makes retries free.

Passage II: a coding-practice site

Questions 33 to 35 refer to this passage.

A coding-practice site runs contests with up to 100,000 participants, and a verdict must come back within five seconds. Each language has its own container image, locked down with a read-only filesystem, CPU and memory limits, a five-second timeout, no network access, and a restricted set of system calls.

Q33LeetCode

At a contest peak, 10,000 submissions arrive together. Each runs 100 test cases at about 100 ms a case, which is the breakdown’s deliberately cautious figure. Roughly how many CPU cores would clear that burst in one minute, and what follows?

Options for question 33

Solution

Answer: C

10,000 submissions × 100 cases × 0.1 seconds is 100,000 seconds of CPU. Spread over 60 seconds, that is about 1,670 cores.

The largest cloud machines have a few hundred virtual CPUs, and one that size would sit idle between contests. So the breakdown rules out scaling up and scales the containers out, with the queue to take up the burst. A and B lose a factor of a hundred or ten on the way. D is the CPU-seconds, not the cores.

Remember Say the arithmetic out loud: seconds of work against cores. It tells you when to scale out.

Q34LeetCode

A participant submits code that contains an infinite loop. What should happen?

Options for question 34

Solution

Answer: D

The job succeeded. Its task was to judge the code, and the judgment is “too slow”. That verdict is a result to store and show, like “wrong answer”.

Retrying (A) would run the same loop again with the same outcome, tie up workers in the middle of a contest, and fill the dead letter queue with things that are not bugs in your system. B has no open request to time out; the submit call returned long ago. C is what the explicit timeout prevents.

The distinction to keep: the user’s code failing is a normal outcome. Your infrastructure failing, such as a worker host dying in the middle of a run, is what retries are for.

Remember A failing verdict is a successful job. Retry infrastructure failures, not user outcomes.

Q35LeetCode

A worker reports a passing verdict and dies before acknowledging, so the same submission is judged and reported a second time. The leaderboard score is the number of problems a user has solved. Which update is safe?

Options for question 35

Solution

Answer: B

ZADD sets the score to a value worked out from the facts. A second report works out the same count and writes the same number.

ZINCRBY adds one on every report, so a job delivered twice gives the user a point they did not earn. It also over-counts someone who passes the same problem twice on purpose, which is why the breakdown’s query counts distinct problems. C keeps the bug and adds a clock. D confuses atomic with idempotent: each increment is applied whole, and each one counts.

The breakdown updates the sorted set with ZADD. The contrast with ZINCRBY is added here.

Remember Set the score from the facts; do not add to it. Atomic is not idempotent.

Passage III: a job scheduler

Questions 36 to 38 refer to this passage.

A job scheduler lets users run a task now, at a future time, or on a recurring schedule. It must start each run within two seconds of its scheduled time, sustain 10,000 runs a second, and guarantee that every run happens at least once. The team designs it as in the figure.

  1. Job definitions live in a Jobs table. Every planned run is a row in an Executions table, grouped by the hour in which it is due.
  2. Every five minutes a scheduler process reads every run that is due before the next sweep and has not been queued yet. It sends each one to SQS with a delivery delay equal to the time left, so the message stays hidden until the run is due.
  3. Workers receive messages as they appear, run the task, write the status to the Executions row, and delete the message. The visibility timeout is 30 seconds.
  4. For a recurring job, the worker inserts the row for the next run when the current one finishes.
Q36Job Scheduler

Ten seconds after a sweep, a user creates a job that is due 90 seconds from now. In the design exactly as written, what happens, and what is the fix?

Options for question 36

Solution

Answer: B

The sweep that would have caught the row has already gone by. The next one arrives 4 minutes 50 seconds later, finds the run overdue, and queues it with no delay. It starts 3 minutes 20 seconds late, against a two-second target.

The fix is at creation: compare the due time with the current window, and if it falls inside, write the row and send the message. C would work, but it turns 10,000 runs a second into every worker polling the database constantly, which is the load the two layers exist to avoid.

The two layers in one line: the database holds everything, cheaply, for as long as needed. The queue holds only what is about to happen, precisely. SQS allows a delay of at most 15 minutes, which is one reason the window is short; that limit comes from AWS, not from the article.

Remember Database for the far future, queue for the next few minutes, and a shortcut for jobs created inside the window.

Q37Job Scheduler

Some tasks run for ten minutes. If a worker crashes, another worker should pick its run up within about 30 seconds. Which arrangement gives both?

Options for question 37

Solution

Answer: C

The extension is a heartbeat. While the worker lives, the message stays hidden. When the worker dies, the extensions stop, and the message reappears within 30 seconds.

A makes long tasks safe but leaves a crashed run undiscovered for up to 15 minutes. B delivers a healthy run again every 30 seconds: several workers run the same task at once, the receive count climbs, and a perfectly good job can end up in the dead letter queue. D means a crash loses the run. That is at most once, and the requirement is at least once.

Extending a visibility timeout is an SQS feature the article does not go into.

Remember A short timeout, extended while alive: quick crash detection without duplicate runs.

Q38Job Scheduler

One recurring job charges a customer’s card on the first of each month. Runs are at-least-once. What makes this safe?

Options for question 38

Solution

Answer: D

The key must be the same for every attempt at one run, and different for different runs. Job ID plus scheduled time is exactly that. A retry of March’s run repeats March’s key and the provider returns the first result, while April’s run has a key of its own.

B changes on every attempt, so it protects nothing. C never changes, so April’s charge is refused as a repeat of March’s.

A sounds like the answer and is not. A FIFO queue removes duplicate sends within a short window. It cannot help when a worker charges the card and dies before deleting the message: the message comes back, and only the key held by the provider stops the second charge. This detail of SQS goes beyond the article.

Remember One key per run: job ID + scheduled time. The same on a retry, new next month.

Passage IV: a chat assistant

Questions 39 to 41 refer to this passage.

A chat product receives about 20,000 prompts a second at peak. An answer takes several seconds to generate, so about 120,000 are streaming at any moment. Users judge it by how soon the first words appear, and GPUs are scarce and expensive. The team settles on the design in the figure.

  1. POST /chats/:id/messages saves the user’s message, creates a run with status queued, and hands it to a scheduler.
  2. The scheduler assigns runs to GPU workers as slots become free.
  3. A worker generates the answer and appends each token to a buffer kept for that run.
  4. The chat service holds the client’s streaming connection, reads the run’s buffer, and forwards tokens as they arrive.
  5. When generation ends, the worker saves the full answer to the database and marks the run completed.
Q39ChatGPT

Half-way through an answer, the user’s phone changes networks. It reconnects three seconds later and lands on a different chat-service instance. What lets the answer continue where it left off?

Options for question 39

Solution

Answer: C

The run never depended on the connection. The worker has been generating and appending to the buffer (step 3) all along; only the delivery in step 4 broke. Any instance can take delivery over if it knows which run, and from where.

A fails whenever the original instance has gone, which is every deploy, and that instance held nothing the buffer does not. B spends scarce GPU time twice and may produce a different answer from the half the user has already read. D leaves the user looking at a frozen half-answer until the end.

Remember Separate the generation from the connection. To resume: run ID + last position.

Q40ChatGPT

The user presses Stop after two sentences. Why must the cancellation reach the GPU worker, instead of only closing the streaming connection?

Options for question 40

Solution

Answer: A

The separation that makes reconnecting work (Q39) also means that a closed connection tells the worker nothing. The worker writes to the buffer, not to the connection (B).

So Stop has to be an explicit signal, such as a flag on the run that the worker checks between tokens. On seeing it the worker stops, saves what it produced, and frees the slot. With GPUs as the scarce resource and runs waiting behind, a slot spent on text nobody will read is the most expensive waste in the system.

Remember Closing the stream does not stop the work. Cancel the run, and free the GPU.

Q41ChatGPT

A surge of free-tier traffic fills the scheduler’s queue. Paid users should still see a fast first token, and no single user should be able to occupy the pool. Which design fits?

Options for question 41

Solution

Answer: D

Three of the article’s tools at once. Separate queues stop one class of work from blocking another; here the classes are tiers, where in the article they were durations. A cap per user keeps one heavy user from holding many slots. A depth limit on the free queue is backpressure: an honest “at capacity” is better than a wait with no end.

A lets the free surge sit in front of paid runs. B is the usual answer for CPU workers, but the passage says GPUs are scarce. You cannot count on more of them arriving in time, so scheduling the ones you have matters more than adding to them. C has nothing to do with priority.

Remember Scarce workers: separate by tier, cap per user, refuse past a depth.
